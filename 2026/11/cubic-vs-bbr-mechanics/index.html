CUBIC 与 BBR 原理对比：发包时序与窗口计算

十一月 19, 2026 [网络与安全] #网络 #协议与标准 #Linux

同样跑在 TCP 上，CUBIC 和 BBR 对"什么时候发包、发多少"的回答完全不同：前者跟着 ACK 走，用三次函数把窗口撑大；后者自己排发送节奏，用带宽和 RTT 的模型算出在途数据上限。下面按"发包时序 → 窗口计算 → 丢包响应"拆开看。

一、总览

维度CUBICBBR
驱动信号丢包 / 重复 ACK带宽估计 + 最小 RTT
发包节奏ACK 时钟（事件驱动）Pacing（时间驱动）
窗口角色增长目标，按三次函数主动撑大在途数据量上限，防止超过 BDP
拥塞响应乘法减小 cwnd * β（β≈0.7）不把丢包直接当带宽信号，靠 ProbeRTT 周期性排空

一句话：CUBIC 是"丢包驱动 + 窗口增长"，BBR 是"模型驱动 + 速率规划"。

二、CUBIC：ACK 时钟与三次函数

2.1 发包时序

CUBIC 仍运行在传统 TCP 框架里，发包由ACK 到达事件驱动：收到能推进 snd_una 的 ACK，才按当前 cwnd 决定还能不能再发。ACK 被压缩或延迟，发包就会呈突发状。

它本身不内置强制性的速率调度。现代内核可以配合 fq qdisc 做 pacing，或退回 TCP 内部的高精度定时器 pacing，但这些是外部机制；CUBIC 算法核心的节奏仍是"事件驱动"。这也是它和 BBR 最根本的差别。

2.2 窗口如何增长

CUBIC 的窗口曲线是一条凹-凸三次曲线，按时间分两段：

  • 凹区（cwnd < W_max）：低于上次拥塞前的窗口，增长较快，目标是把窗口迅速恢复到接近 W_max。
  • 凸区（cwnd > W_max）：超过旧上限后，增速放缓，小心试探新的带宽上限。

核心公式：

W_cubic(t) = C * (t - K)^3 + W_max
  • t：距上次拥塞事件的时间
  • W_max：上次拥塞前的窗口
  • C：常数，论文取 0.4
  • K：从当前窗口增长回 W_max 所需的时间

每收到一个 ACK，CUBIC 用公式算出当前的目标窗口 W_cubic(t)，再决定本次该给 cwnd 加多少。

Linux 实现里并不直接照抄浮点公式，而是用定点数（BICTCP_HZ = 10）预计算 cube_factor / cube_rtt_scale：论文里的 C 被拆成 c = bic_scale / 1024 ≈ 0.04，再除以 100 ms 的参考 RTT，得到 c/rtt ≈ 0.4/s。真正决定"每个 ACK 涨多少"的是 ca->cnt：目标窗口与当前窗口差得越多，cnt 越小，增长越快。

另外 Linux 还做了两件补丁：

  • TCP friendliness：维护一条 Reno 基准曲线，CUBIC 增长慢于 Reno 时抬到 Reno 的速率，避免高 RTT 链路上饿死 Reno 流。
  • HyStart：慢启动阶段用 ACK train / 延迟上升来提前退出，减少启动期丢包。

2.3 RTT 是测出来的吗？

是，而且一直在变。 每收到一个有效 ACK，内核用"当前时间 − 该数据段发送时间"得到一个 RTT 样本，交给 tcp_ack_update_rtt() 更新平滑值 srtt_us。没有有效样本时内部会用 -1 之类的哨兵值表示"本次不算"，这个哨兵不会被当成 RTT 传给拥塞控制。

但要注意 CUBIC 对 RTT 的使用方式：

  • 理论上，W_cubic(t) 的 t 是墙钟时间，公式本身不需要 RTT。
  • 实际上窗口增长按 ACK 触发，要把"每秒涨多少"折算成"每个 ACK 涨多少"，就必须知道每秒有多少个 ACK，也就是 cwnd / RTT。RTT 变了，同样的 cnt 对应的实际增速也会变。
  • Linux 实现还额外把最小 RTT（ca->delay_min）加到时间轴上（t += delay_min），也就是说曲线并非从 t=0 起算，而是从 t = delay_min 处起算；K 则在每次拥塞事件开启新 epoch 时重算一次，而不是每个 ACK 重算。

所以准确说法是：CUBIC 的曲线是时间函数，但落地到 ACK 时钟时依赖 RTT 估计；RTT 由 ACK 驱动持续测量并平滑。

2.4 K 值怎么来

K 不是测量值，是从公式反推的。

拥塞事件后窗口被乘性减小到 cwnd_start（近似 W_max * β，β≈0.7）。令 t = 0 时 W_cubic(0) = cwnd_start：

cwnd_start = C * (0 - K)^3 + W_max

解得：

K = ∛((W_max - cwnd_start) / C)

Linux 的 bictcp_update() 里对应：

if (ca->last_max_cwnd <= cwnd) {
        ca->bic_K = 0;
        ca->bic_origin_point = cwnd;
} else {
        ca->bic_K = cubic_root(cube_factor
                               * (ca->last_max_cwnd - cwnd));
        ca->bic_origin_point = ca->last_max_cwnd;
}

几个特殊情形：

  • 当前窗口已经不低于 W_max（例如超时后重置、或新流首次进入拥塞避免），K 直接为 0。
  • 开启 Fast Convergence 时，如果本次 cwnd < last_max_cwnd，会先把 W_max 压低到 cwnd * (1+β)/2，给新流让出空间；K 用压低后的 W_max 计算。
  • 超时后的第一次拥塞避免走 bictcp_reset() 路径，last_max_cwnd 和 epoch 清零，相当于重新起一条曲线。

2.5 丢包响应

检测到丢包（重复 ACK / RACK 判定）后，CUBIC 做乘性减小：

cwnd = cwnd * β

Linux 默认 beta = 717/1024 ≈ 0.7，比 Reno 的 0.5 温和。之后窗口从降低后的值重新沿三次曲线爬向新的 W_max。所以 CUBIC 的吞吐曲线在瓶颈队列里通常呈锯齿状，对缓冲区深度很敏感。

三、BBR：Pacing 主导 + BDP 窗口

BBR 抛开了"丢包即拥塞"的假设。它维护两个模型量：

  • BtlBw：瓶颈带宽，取最近约 10 个 RTT 内交付速率的最大值（窗口化最大值，滤掉测量噪声）
  • RTprop：最小 RTT，取最近 10 秒内的最小值（窗口化最小值，只在 ProbeRTT 时刷新）

然后：

pacing_rate = pacing_gain * BtlBw
BDP         = BtlBw * RTprop
cwnd        ≈ cwnd_gain * BDP

3.1 发包时序：Pacing

BBR 的核心是 pacing：估算出 BtlBw 后，按 pacing_gain * BtlBw 的速率把包均匀撒出去，而不是等 ACK 攒够一批再突发。

稳定态是 ProbeBW，一个 8 相的增益循环：

  • UP 相：pacing_gain = 1.25，比估计带宽多发 25%，试探还有没有余量。若瓶颈排队，RTT 会上升，但 BBR 不会立刻退让。
  • DOWN 相：pacing_gain = 0.75，把 UP 相可能攒出的队列排掉。
  • CRUISE 相：pacing_gain = 1.0，按估计带宽匀速发送。

循环是 1.25, 0.75, 1, 1, 1, 1, 1, 1，每相约一个 RTT 量级，正好覆盖"挤压 → 放松 → 巡航"的完整探测周期。

此外还有两个阶段：

  • STARTUP：pacing_gain = 2/ln2 ≈ 2.885，每个 RTT 翻倍，快速找到初始带宽。
  • DRAIN：增益取 1/2.885 ≈ 0.35，把 STARTUP 期间积攒的队列排空。

3.2 窗口如何计算

BBR 不主动"撑大"窗口，cwnd 是防止在途数据超过 BDP 的保险丝：

cwnd = max(cwnd_gain * BtlBw * RTprop, 4)

Linux 里 bbr_cwnd_gain = 2，bbr_cwnd_min_target = 4 个包。乘以 2 是为了容忍 ACK 聚合、延迟 ACK 和突发，而不是为了增长。

真正会主动压窗口的是 ProbeRTT：如果连续 10 秒没有采到更小的 RTT，BBR 进入 ProbeRTT，把 cwnd 压到 4 个包并至少保持 200 ms，排空瓶颈队列以测到真实的 RTprop，然后恢复。这对应源码里的 bbr_probe_rtt_mode_ms = 200、bbr_min_rtt_win_sec = 10、bbr_cwnd_min_target = 4。

3.3 丢包和 ECN 怎么处理

BBRv1 的带宽模型不看丢包，也不看 ECN：

  • 丢包不会让 pacing_rate 直接下降；它可能短暂影响 cwnd，BBR 在恢复后会把 prev_cwnd 还原。
  • ECN 的 CE 标记只走 TCP 通用的 cwnd 减小流程，不会改变 BBR 的 BtlBw 估计。
  • 真正的降速来自 ProbeBW 的 DOWN 相和 ProbeRTT 的排空。

这是 BBRv1 的取舍：在浅缓冲、有随机丢包的链路上吞吐稳，但在深缓冲队列里可能占队过多、对丢包流不公平。BBRv2/v3 才引入丢包率、ECN 和更明确的公平性机制（主线内核目前仍是 BBRv1 实现）。

四、实际表现

  • CUBIC：平时按三次函数缓慢加窗，撞上丢包砍一刀再爬回来。吞吐呈锯齿状，受 buffer 深度影响大；RTT 越短、丢包越少，恢复越快。
  • BBR：以 ProbeBW 循环持续采样带宽，窗口只做上限。随机丢包下吞吐更稳，排队延迟通常更低；代价是 ProbeRTT 的周期性排空会带来轻微吞吐抖动，多流共存时公平性不如 CUBIC。

选择上：

  • 跨境、无线、有随机丢包的链路 → BBR 通常更稳
  • 同机房、低延迟、多流公平性优先 → CUBIC 仍然合适
  • 开了 BBR 但 qdisc 是 fq_codel，建议换成 fq，让 pacing 走 qdisc 而不是每个 socket 一个高精度定时器

验证当前连接用的是哪种算法、窗口和 pacing 状态：

sysctl net.ipv4.tcp_congestion_control net.core.default_qdisc
ss -ti dst :443
# BBR 连接会额外显示 bbr:(bw,rtt,pacing_rate)，以及 cwnd/rtt

问题CUBICBBR

六、源码位置

想对照实现，直接看这两个文件：

  • net/ipv4/tcp_cubic.c
    • bictcp_update()：三次曲线目标窗口与 ca->cnt
    • cubictcp_cong_avoid()：按 ACK 推进 cwnd
    • cubictcp_recalc_ssthresh()：乘性减小、Fast Convergence、W_max 更新
    • cubictcp_state()：超时/恢复状态切换时重置曲线
  • net/ipv4/tcp_bbr.c
    • bbr_update_bw()：更新 BtlBw
    • bbr_set_pacing_rate()：pacing_gain * BtlBw
    • bbr_set_cwnd()：cwnd_gain * BDP 上限
    • bbr_update_cycle_phase()：ProbeBW 的 8 相循环
    • bbr_check_probe_rtt_done()：ProbeRTT 退出条件

参数速记：CYCLE_LEN = 8、bbr_cwnd_gain = 2、bbr_probe_rtt_mode_ms = 200、bbr_min_rtt_win_sec = 10、bbr_cwnd_min_target = 4。
