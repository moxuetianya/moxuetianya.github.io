git push 不止推 GitHub：SSH 直推远端仓库与非 bare 的 updateInstead

十一月 20, 2026 [Linux 与系统] #Git #SSH #deployment

背景：没有 GitHub key 的机器，怎么同步代码

场景：本地和一台 DUT（dut2）各有一份同一仓库的 checkout，远端在 GitHub。某天 DUT 落后了 10 个提交，想同步过去，却发现：

$ git pull --ff-only
git@github.com: Permission denied (publickey).

DUT 上既没有记录 GitHub 的 host key，也没有部署 key。往 GitHub 加 key 固然是一条路，但这里 有个更直接的认知：git push 从来不绑定 GitHub——任何我能 ssh 上去的机器上的 git 仓库， 都可以当远端推：

GPG_TTY=/dev/nonexistent git push ssh://dut2/home/smyl/project/learn-wayland master
# To ssh://dut2/home/smyl/project/learn-wayland
#    8dcafbb..e6a9746  master -> master

一条命令，dut2 上的仓库和工作树一起更新到最新。这篇文章拆开讲它为什么成立、推非 bare 仓库为什么要先配置、以及它和推 GitHub 的异同。

原理：git push 推的到底是什么

git push <URL> <branch> 的本质是两端的 git 进程在对话：

本地 git-send-pack
   │  ssh 登录 dut2，在远端执行：
   │      git-receive-pack /home/smyl/project/learn-wayland
   │  传输 pack（对象）→ 请求更新 refs/heads/master
   ▼
远端 git-receive-pack 校验并落盘 → refs/heads/master 指向新提交

推 GitHub 时（git push origin master，origin = git@github.com:user/repo.git）发生的是 同一件事：sshd 收到请求后在服务器上执行 git-receive-pack，收到对象、挪动 ref。 GitHub 只是在外面套了认证、权限、web 界面和一堆服务端 hook。把 URL 换成 ssh://dut2/路径，对端从"GitHub 的机器"变成"我的机器"，协议层一个字节都没变。

所以「能不能推」的唯一前提是：远端能跑 git-receive-pack，且我有 ssh 权限。

bare 与非 bare：.git 目录里有什么不一样

结构：bare = 只有 .git 那部分

用同一仓库实测对比（bare 那份是 git clone --bare 出来的）：

=== bare 仓库 ===
branches  config  description  HEAD  hooks  info  objects  packed-refs  refs

=== 非 bare 的 .git ===
branches  config  description  HEAD  hooks  info  objects  packed-refs  refs
（另有）COMMIT_EDITMSG  FETCH_HEAD  index  logs  ORIG_HEAD  ……
条目bare非 bare说明
HEAD / refs/ / objects/ / hooks/ / config有有仓库本体，两边同构
core.baretruefalse决定 git 是否允许它检出工作树
index无有暂存区状态——没有工作树自然没有暂存
logs/（reflog）默认无有本地操作痕迹，服务端基本用不上

也就是说：bare 仓库就是「把 .git 目录的内容提升为仓库根目录」，仅此而已。

数据：和 GitHub 上的一样吗？

「我本地的 .git 和 GitHub 存的是同一份数据吗？」——同格式、同内容寻址，但集合不一定相等：

  • 格式与内容完全同构：git 对象是内容寻址的（SHA-1/SHA-256 由内容算出），同一个提交在 两边就是同一个哈希。实测两边 rev-parse master 都是 e6a9746...，逐字节一致——这是 内容寻址的必然，和松散对象还是 packfile、谁压缩得狠无关。
  • 集合可以不相等：本地可能有未 push 的提交、reflog 里的历史悬空对象；远端可能有别人 push 的分支、平台专属的 ref（如 GitHub 的 PR ref）。两边是互相超集关系，push/pull 就是在做增量对齐。
  • GitHub 服务端那份，逻辑上就是一个挂满 hook 的 bare 仓库。

直推非 bare 仓库：receive.denyCurrentBranch

默认为什么拒绝

GitHub/GitLab 服务端是 bare 仓库，推过去只动 ref，没有任何工作树需要操心。但 dut2 上是 普通 checkout，master 正被检出——push 只更新 ref 和对象，不会碰工作树。如果放任直推， dut2 上 git log 已经是新提交、磁盘上的文件却还是旧内容，HEAD 和工作树就此分裂。

所以 git 对非 bare 仓库默认拒绝推当前检出分支：

remote: error: refusing to update checked out branch: refs/heads/master

（早先版本表现为 receive.denyCurrentBranch 相关提示，语义相同。）

updateInstead：干净就连工作树一起更

解法是在远端仓库配置一次：

git config receive.denyCurrentBranch updateInstead

各取值的语义：

取值行为
refuse（默认）拒绝推当前检出分支
ignore / warn允许，但工作树留在旧状态（分裂，慎用）
updateInstead工作树与暂存区干净、且没有会被覆盖的未跟踪文件时，收包后顺手把工作树检出到新 HEAD；否则拒收保护

配好后本机直推，dut2 的仓库和工作树同步前进，之后在 dut2 上 grep 新内容立即命中。

用法速记

# 远端一次性配置（每个非 bare 仓库都要）
git config receive.denyCurrentBranch updateInstead

# 本机直推：两种 URL 写法
git push ssh://dut2/home/smyl/project/learn-wayland master   # 绝对路径
git push dut2:project/learn-wayland master                   # scp 风格，相对家目录

# 用得频繁就命名成 remote
git remote add dut2 ssh://dut2/home/smyl/project/learn-wayland
git push dut2 master

两个细节：

  • GPG_TTY=/dev/nonexistent 前缀与推 GitHub 时相同：key 由 gpg-agent 管理时防止 pinentry 弹窗把命令挂住，失败会立即报 agent refused operation。
  • 直推不更新远端对它自己 origin 的认知，dut2 的 git status 可能显示假 ahead，fetch 一次即消失，无害。

这就是「最简部署」的形态

服务器配 updateInstead（或 post-receive hook），本地一条 git push 完成发布——这是 git 部署的经典手法，本文的 dut2 同步就是它的最小版本。选择上：

  • 个人机器间同步 / 单人部署：updateInstead 足够，零额外设施。
  • 正式部署：服务器放 bare 仓库 + post-receive hook（检出到 web 目录、重启服务）， 工作树与仓库分离，还能叠加回滚逻辑。
  • 多人协作：回到 GitHub/Gitea 等平台——认证、权限、PR 这些 push 协议本身不管的事， 才是平台的价值所在。

顺带一提，本地裸仓库还能直接当 origin 承接 push，配合 Git LFS 的玩法见 给本地裸仓库启用 Git LFS。

总结

  • git push = 本地 send-pack 经任意传输（ssh/https/file）驱动远端 receive-pack， GitHub 不是必要条件；
  • bare 仓库与非 bare 的 .git 同构，差异只在有无 index/reflog 等工作痕迹；
  • 两边数据同格式同哈希，但对象集合互为超集，push/pull 做增量对齐；
  • 直推非 bare 的检出分支要先配 receive.denyCurrentBranch=updateInstead，它以 「工作树干净」为前提，脏则拒收，不会弄丢远端未提交内容。
