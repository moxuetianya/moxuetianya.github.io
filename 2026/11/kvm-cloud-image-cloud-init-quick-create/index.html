KVM 用 Cloud Image + cloud-init 分钟级创建虚拟机：从原理到实操

十一月 18, 2026 [虚拟化与容器] #kvm #libvirt #qemu #虚拟化

需求：快速再来一台干净的虚拟机

一台 aarch64 KVM 宿主机（libvirt 8.0 / QEMU 6.2，ARM 服务器）上已经跑着一台 Ubuntu 24.04 开发机 dev-vm：

  • 磁盘 /data/vm/dev-vm.qcow2，qcow2 精简置备，虚拟 300G、实际占用 234G（盘内真实数据 175G：/data 81G + /var 约 72G 的 docker + /home 21G）
  • UEFI（AAVMF secure boot 变体）+ virt-6.2 机型，macvtap 直连物理网卡，cloud-init 出身（挂着 seed.iso）

现在要快速再创建一台新虚拟机，三个硬性要求：

  1. 不修改原来的 dev-vm（盘文件一个字节都不能动）；
  2. 与原机没有任何共享（排除 qcow2 backing file 这类共享基础镜像的方案）；
  3. 新机只要 100G 盘。

原盘实际数据 175G > 100G，这个矛盾直接决定了技术选型。

选型：三条路线对比

路线做法耗时评价
完整克隆qemu-img convert 全拷 234G → 新机内删 /data、清 docker → 在线缩 ext4 + 缩盘到 100G1 小时+步骤多；ext4/GPT 缩盘有风险；违背"快速"
完整克隆但放弃 100G全拷后直接用 200G+ 的盘30-60 分钟可行，但违背 100G 约束
全新 cloud image用官方 cloud 镜像 + cloud-init 造一台干净新机几分钟数据不带走（确实也不需要），系统底座与原机同版；软件按需重装

选第三条。因为"根据原机创建"的真实诉求是要一台同款系统的机器，不是要那 175G 数据——数据大头是 docker 镜像和 /data 数据集，新机上要么不需要、要么可重新拉取。

Cloud image 与 Desktop ISO 的本质区别

很多人第一次接触 cloud image 会疑惑它和 ubuntu-24.04-desktop-amd64.iso 有什么区别——一个是"装好的系统盘"，一个是"安装程序"：

Desktop ISOCloud image
本质光盘安装介质：live 系统 + 图形安装器现成的磁盘镜像（qcow2），系统已预装好
体积~6 GB~600 MB
装机方式挂 ISO → VNC 图形 console → 人工点分区/建用户，10-20 分钟virt-install --import 直接从盘启动，cloud-init 首启自动初始化，1-2 分钟出机
预装内容GNOME 桌面、浏览器、办公全家桶极简 server：无桌面；但预装 cloud-init、ssh、qemu-guest-agent
默认账户安装时人工创建ubuntu 用户，密码锁定、仅 SSH key 登录，root 禁用
分区设计安装时人工定死root 分区特意放在分区表最后，growpart/resizefs 首启自动扩满整盘

最后一行是"直接 resize 到 100G"能成立的原因。

另外两个发行版层面的细节：

  • 下载地址：官方 cloud-images.ubuntu.com/<代号>/current/（noble=24.04、jammy=22.04），国内清华镜像 mirrors.tuna.tsinghua.edu.cn/ubuntu-cloud-images/ 同步且快得多。文件名带架构：...-arm64.img / ...-amd64.img，取 .img（qcow2），别取 .sqsh/.vhd 等云平台专用变体。
  • 架构必须对：这次宿主机上正好躺着一张历史的 ubuntu-24.04.1-desktop-amd64.iso，但宿主是 aarch64，amd64 的 ISO 根本装不了——ARM 机器上别拿错。

原理篇：四个关键问题

1. 镜像复制的本质——不是 dd，是 qemu-img convert

把 cloud image 变成新机磁盘，语义上是"整盘复制"，但实现不用 dd：

ddqemu-img convert
工作层次逐字节块盲拷，不理解内容格式感知：解析 qcow2 结构，只拷"已分配的簇"
数据量拷全部（含空洞）只拷有效数据，跳过全零簇，可顺带压缩/转格式

之后的 qemu-img resize 100G 更轻：只改 qcow2 头里的"虚拟大小"字段（纯元数据操作，秒级），不搬数据。guest 看到的盘瞬间变 100G，旧数据在低地址原封不动，新增部分是未分配的"零"——首启 cloud-init 的 growpart + resizefs 把根分区扩满。

qemu-img convert -f qcow2 -O qcow2 noble-server-cloudimg-arm64.img dev-vm-2.qcow2
qemu-img resize dev-vm-2.qcow2 100G
chown libvirt-qemu:kvm dev-vm-2.qcow2 && chmod 664 dev-vm-2.qcow2

2. 为什么必须要 seed.iso——cloud image 是"无菌"镜像

cloud-init 首启要回答"我是谁、允许谁登录"，这些信息设计上就不在镜像里（否则全世界同一张镜像的机器都有相同的用户/密码/主机名）。配置必须从外部注入，来源叫 datasource：

  • 云上（EC2 等）：guest 起网后去 169.254.169.254 元数据服务拿；
  • 本地 KVM：没有这种服务 → NoCloud 方案——把 user-data 和 meta-data 打成一个小 ISO 挂成光驱。

不给 seed 的后果：cloud-init 找不到数据源，等待超时（拖慢启动 1-2 分钟），然后按镜像默认值跑——ubuntu 用户密码锁定、无 key、root 禁用 → 一个都登不进去。这是安全特性：镜像可以随便公开传播，钥匙永远由部署者现场注入。

meta-data 里的 instance-id 是实例身份——同一张 seed 挂到第二台机器，cloud-init 认为"还是那个实例"，per-instance 初始化（hostname/用户/key）不再重跑。这也是克隆现有虚拟机时必须重新生成 seed 的原因（克隆路线还有 MAC 地址、/etc/machine-id 两个要去重的）。

3. 卷标 cidata——可重复的"接头暗号"

genisoimage 打包时的 -volid cidata 常被照抄却不知所以然。卷标（volume label）是给一个卷（文件系统/分区/光盘镜像）起的人可读名字，写在文件系统自己的元数据里：

文件系统卷标存放位置
ISO 9660主卷描述符（镜像偏移 32808）里的 Volume Identifier，32 字节
ext4超级块里的 s_volume_name，16 字节
vfat/FAT32根目录区的卷标项

可以直接从现成 seed.iso 里把这 32 字节抠出来验证：

$ dd if=seed.iso bs=1 skip=32808 count=32 2>/dev/null
cidata

卷标可以重复——它设计上就是给人看的名字，没有唯一性校验；承担唯一性职责的是 UUID（fstab/挂载靠它）。cloud-init 的 NoCloud 检测正是利用这点：它不知道配置盘会出现在哪个设备名（/dev/sr0？/dev/vdb？），于是开机枚举所有块设备，谁符合「文件系统 iso9660/vfat 且卷标 == cidata」就认谁。这不是"身份证比对"，是"接头暗号"：全世界所有 NoCloud seed 盘共用同一个名字，靠约定俗成工作；一台 VM 只挂一个 seed，重复也无所谓。

卷标重复真正会碍事的只有 mount -L 卷标名（按卷标挂载）这类场景。日常操作小抄：

lsblk -o NAME,FSTYPE,LABEL,UUID   # 总览
blkid /dev/vda1                    # 单设备详情
e2label /dev/vda1 mydisk           # 改 ext4 卷标
mkfs.ext4 -L mydisk /dev/vdb1      # 格式化时定名

4. virt-install --import 对 qemu 零影响

QEMU 本身没有"安装"这个概念——它只管"给我盘我就跑"。区别全在 virt-install 生成 libvirt domain XML 的策略：

  • 普通安装（两阶段）：建空盘 → 挂安装 ISO（或 -kernel/-initrd 直启安装器）→ 安装器把系统写进盘 → virt-install 收到完成信号 → 改写 XML（卸安装介质、boot 改硬盘）→ 重启进新系统；
  • --import（一步）：声明"这盘里已是可启动系统"，生成的 XML 从一开始就是 <boot dev='hd'/>，define + start 完事。省掉的"安装阶段"由 cloud-init 在 guest 内部接管。

实证：ps 抓一台 --import 出身的运行中 VM 的 qemu 命令行（tr '\0' '\n' < /proc/<pid>/cmdline），关键部分是：

-drive file=/usr/share/AAVMF/AAVMF_CODE.ms.fd,...       # pflash0 固件
-drive file=/var/lib/libvirt/qemu/nvram/..._VARS.fd,... # pflash1 NVRAM
-machine virt-6.2,...,pflash0=...,pflash1=...
-drive file=/data/vm/dev-vm.qcow2,...                    # 系统盘
-device virtio-blk-pci,...,bootindex=1
-drive file=/data/vm/seed.iso,...                        # cloud-init 配置盘

没有 -kernel/-initrd/-append（直启安装器才需要），也没有安装 ISO。qemu 层面收到的和任何"从硬盘启动的 VM"一模一样。

附：cloud-init 不是虚拟机专属

cloud-init 对环境没有硬性要求，唯一需求是开机时能从某处拿到配置。物理机的玩法：

  • MAAS（Canonical 官方裸机置备）：物理机 PXE 网启 → MAAS 把 cloud image 直接写盘 → 首启 cloud-init 找 MAAS 要身份，"物理机像云主机一样即插即用"；
  • U 盘/第二块盘：FAT/ext4 卷标 cidata 均可（NoCloud 不强制 ISO），插上就行；
  • kernel 启动参数：grub 里加 ds=nocloud-net;s=http://provision-server/，开机从 HTTP 拉 user-data；
  • 树莓派官方 Ubuntu 镜像同理：烧完盘把 user-data 丢进 system-boot 分区，首启自动配置。

与传统裸机安装的定位差异：preseed / kickstart / autoinstall 是自动化"安装器"（装系统时自动回答分区/选包），cloud-init 是首启注入"身份"（用户/key/hostname/网络）——两者是配合关系，MAAS 的完整链路就是 PXE 写盘 + cloud-init 收尾。

实操：完整流程

① 做盘（独立、零共享）

qemu-img convert -f qcow2 -O qcow2 /data/vm/noble-server-cloudimg-arm64.img /data/vm/dev-vm-2.qcow2
qemu-img resize /data/vm/dev-vm-2.qcow2 100G
chown libvirt-qemu:kvm /data/vm/dev-vm-2.qcow2 && chmod 664 /data/vm/dev-vm-2.qcow2
qemu-img info /data/vm/dev-vm-2.qcow2
# virtual size: 100 GiB / file format: qcow2 / 无 backing file

convert 读源镜像一次、产出完全独立的新文件——即使源镜像与原机当年用过的是同一张 cloud image，也不构成与运行中 VM 的任何共享（cloud image 只是"安装介质"性质的源材料）。

② 写 user-data

#cloud-config
hostname: dev-vm-2
manage_etc_hosts: true
users:
  - default
  - name: dev
    sudo: ALL=(ALL) NOPASSWD:ALL
    groups: [sudo]
    shell: /bin/bash
    lock_passwd: true
    ssh_authorized_keys:
      - ssh-ed25519 AAAA... <你的公钥>
ssh_pwauth: false
disable_root: true
package_update: false
growpart:
  mode: auto
  devices: ['/']
resize_rootfs: true

要点：lock_passwd: true + ssh_pwauth: false = 只能 key 登录。别预设 docker 组——cloud image 里该组不存在时 useradd -G 会报错导致用户创建失败，装 docker 时再加。

③ 启动

virt-install \
  --connect qemu:///system \
  --name dev-vm-2 \
  --memory 16384 --vcpus 16 \
  --cpu host --machine virt-6.2 \
  --boot loader=/usr/share/AAVMF/AAVMF_CODE.ms.fd,loader_ro=yes,loader_type=pflash,nvram_template=/usr/share/AAVMF/AAVMF_VARS.ms.fd \
  --import \
  --disk /data/vm/dev-vm-2.qcow2,bus=virtio,format=qcow2 \
  --network type=direct,source=enp2s0f0,source_mode=bridge,model=virtio \
  --cloud-init user-data=/tmp/dev-vm-2-user-data \
  --noautoconsole --autostart

三个细节：

  • --cloud-init user-data=文件 让 virt-install 自动生成 seed（含唯一 instance-id、正确的 cidata 卷标 ISO 并挂载），替掉手工程序：写 meta-data、genisoimage -volid cidata -joliet -rock user-data meta-data（两个坑：卷标必须 cidata，文件名必须是 user-data/meta-data；偷懒可用 cloud-localds）；
  • ARM 上要显式指定 AAVMF loader：这台宿主的 osinfo-db 太老不认识 Ubuntu 24.04（osinfo-query os 查不到），--os-variant 靠不住；loader 路径从原机 virsh dumpxml 的 <os> 段照抄（secure boot 的 .ms.fd 变体，cloud image 的签名内核支持）；
  • MAC 不指定则自动随机，不会与原机冲突。

④ 拿 IP、验证

# cloud image 自带 qemu-guest-agent，起机后 1-2 分钟可直接问 libvirt 要 IP
virsh domifaddr dev-vm-2 --source agent

# 兜底：宿主机上按 MAC 查 arp 表（ip neigh | grep <MAC>）

ssh dev@<IP>
$ lsblk; df -h /     # 根分区已自动扩到 100G（growpart + resizefs 生效）

Cockpit Machines WebUI 能做同样的事吗

能，cockpit-machines（249+ 均可）的 Create VM 对话框与手工步骤对应关系：

手工步骤WebUI 位置
下载镜像 + convert/resize❌ 无内置——先在 Terminal 页跑命令
virt-install --importInstallation Type 选 "Existing disk image on the host computer"
--cloud-init（自动 seed）对话框 Automation / Cloud-init 区块（root 密码 + SSH key）
内存/vCPU/autostart对话框表单
拿 IPVM 详情页网卡卡片（guest-agent 采集）

局限：

  1. cloud-init 字段太少：只有 root 密码、SSH key 两三个框，"自定义用户 + sudo NOPASSWD + 禁密码登录"这种完整 user-data 表达不了；
  2. 网络是最大的坑：创建对话框基本只给虚拟网络（NAT）选项，macvtap 直连（direct + 物理口）在 UI 里选不到，得创建后 virsh edit 补。且两种拓扑的宿主机访问性正好相反：macvtap 下 guest 拿 LAN IP、LAN 内机器随便访问，但宿主机反而 ping 不通 guest（macvtap 经典限制）；NAT 下宿主可直接 ssh guest，但 LAN 其他机器进不来；
  3. osinfo-db 同样老，OS 列表没有 24.04。

结论：WebUI 适合"快速起一台标准 NAT 网络的机器"；要复刻现有机器的 macvtap 直连 + 自定义用户体系，命令行一步到位。

坑与要点总结

  • 数据量矛盾先算清：克隆路线前先看原盘实际占用（qemu-img info 的 disk size、盘内 df），超出目标盘就只能清理或缩盘，别硬上；
  • 运行中的 qcow2 直接拷贝是崩溃一致性：要么短暂关机再 convert，要么用 virsh blockcopy 在线镜像（不碰原盘）；
  • 克隆现有 VM 必须换三样：MAC 地址、seed 的 instance-id（否则 cloud-init 不重跑）、/etc/machine-id（否则 DHCP 拿到重复 IP）；
  • 无 seed = 登不进去：cloud image 默认账户全部锁定，是安全设计不是 bug；
  • ARM 上别拿 amd64 ISO；osinfo-db 老就用显式 --boot loader=...；
  • 存储池文件属主：libvirt-qemu:kvm + 664，对齐 virsh pool-info 里其他卷的姿势；
  • cloud-init 不只属于虚拟机：MAAS/U 盘/kernel cmdline/SMBIOS 都能喂配置，物理机一样用。

总结

"快速造一台干净的 KVM 虚拟机"这件事，cloud image + cloud-init + virt-install --import 是最优解：分钟级出机、无人值守、身份与钥匙部署时注入、盘大小随意（首启自动扩满）。理解三个核心概念后整个流程再无黑盒：cloud image 是装好的系统盘（与安装器 ISO 本质不同）、seed.iso 是 cloud-init 的配置来源（靠 cidata 卷标接头）、--import 只是让 virt-install 跳过安装阶段直接从盘启动（qemu 层面没有任何特殊之处）。
