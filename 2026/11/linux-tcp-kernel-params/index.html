Linux TCP 内核参数解析：BBR、ECN 与缓冲区调优

十一月 19, 2026 [网络与安全] #网络 #Linux #协议与标准

手里有一份服务器的 net.ipv4.* 快照，逐项看下来有几处容易望文生义：tcp_ecn = 2 到底开没开 ECN、tcp_rmem 的三个数怎么配合自动调优、tcp_tw_reuse = 2 是不是把所有 TIME_WAIT 都复用了。顺手也澄清一个常见疑问：服务端是不是调用了 accept() 才开始接收 SYN。

查看当前值：

sysctl -a | grep -E '^net\.ipv4\.tcp_'
# 或者只挑本文关注的
sysctl net.ipv4.tcp_congestion_control net.ipv4.tcp_ecn \
       net.ipv4.tcp_rmem net.ipv4.tcp_wmem net.ipv4.tcp_mem \
       net.ipv4.tcp_tw_reuse net.ipv4.tcp_retries2

一、拥塞控制

BBR

tcp_congestion_control = bbr。默认通常是 cubic。

BBR（Bottleneck Bandwidth and RTT）不把丢包当作拥塞信号，而是维护两个模型量：窗口化的瓶颈带宽 BtlBw 和窗口化的最小 RTT RTprop，再用 pacing 主动安排发送速率。它不靠"撞到丢包再退让"，所以在有随机丢包、带宽时延积又大的链路上，吞吐通常比 CUBIC 稳定；代价是排队延迟和流间公平性不如丢包驱动算法。

机制细节单独整理了一篇：CUBIC 与 BBR 原理对比；实测数据见 开启 TCP BBR 实测。这里只记结论：拥塞控制只在发送端生效，下载场景里接收方开 BBR 不改变速度。

两个配套参数：

  • tcp_allowed_congestion_control：非特权进程可选的算法集合
  • tcp_available_congestion_control：内核当前已加载的全部算法

快照里两者都是 reno cubic bbr。tcp_congestion_control 只能从 available 里选，普通进程写时还必须落在 allowed 之内。要确认 BBR 模块确实加载，看 /sys/module/tcp_bbr。

tcp_ecn = 2

现代内核的 tcp_ecn 是一个模式值，不是简单开关：

值入站连接出站连接
0不启用不启用
1ECN请求 ECN
2ECN不请求（默认）
3AccECNAccECN
4AccECNECN
5AccECN不请求

所以 2 的含义是：别人连进来时，如果对端请求 ECN 就配合；自己主动连出去时不请求。这是内核默认值，属于保守兼容策略，不是有人刻意打开的。3~5 涉及 Accurate ECN（RFC 9768），普通场景基本用不到。

tcp_fastopen = 1

TFO 用位掩码表示：0x1 客户端、0x2 服务端，3 即两者都开。当前值是 1，只开了客户端。

注意 TFO 的客户端支持不会改变 connect() 的行为——应用必须用 sendto()/sendmsg() 加 MSG_FASTOPEN 显式把数据塞进 SYN。开了 sysctl 不等于所有连接都自动省一个 RTT。

二、连接建立与异常处理

  • tcp_syncookies = 1：SYN 队列溢出时启用 SYN Cookie。这是兜底，不是常规手段——内核文档明确说不能用它支撑合法的连接速率；频繁触发应当去调 backlog、accept 速度或 tcp_synack_retries。
  • tcp_max_syn_backlog = 2048：SYN_RECV 队列上限。内核文档把它描述为 per-listener 限制，实际还会和 listen(backlog)、net.core.somaxconn 一起决定队列深度。
  • tcp_syn_retries = 6：主动连接 SYN 最多重传 6 次。按当前 1 秒初始 RTO，最后一次重传约在 67 秒，最终放弃约在 131 秒。
  • tcp_synack_retries = 5：被动连接 SYN-ACK 重传 5 次，最终超时约 63 秒。
  • tcp_abort_on_overflow = 0：accept 队列满时不发 RST，而是丢掉完成握手的 ACK。客户端会重传，给服务端留出排空队列的时间。设成 1 能让客户端快速失败，但突发流量下容易误伤。
  • tcp_slow_start_after_idle = 1：空闲超过一个 RTO 后重置拥塞窗口（RFC 2861），重新慢启动。保守但安全；长连接、高吞吐且流量呈间歇突发的场景可以评估设为 0。

关键澄清：服务端是在 accept 之后才接收 SYN 吗？

不是。 三次握手完全由内核协议栈自主完成，不需要用户态调用 accept() 来触发。

  1. listen() 之后内核就开始处理到达的 SYN，此时 accept() 还没被调用。
  2. 内核维护两个队列：
    • 半连接队列（SYN 队列）：收到 SYN、尚未完成握手，状态 SYN_RECV。
    • 全连接队列（accept 队列）：三次握手已完成、状态 ESTABLISHED，等待应用 accept() 取走。
  3. accept() 只是从全连接队列头部取一个已建立的连接，返回新 fd，不参与握手。

即使应用迟迟不 accept()，内核也会继续完成握手并把连接放进全连接队列。这正是 tcp_abort_on_overflow 有意义的前提：队列满之后，对后续完成握手的连接是丢 ACK 还是回 RST。

全连接队列的上限是 min(listen(backlog), net.core.somaxconn)。排查时可以直接看监听套接字：

ss -lnt sport = :80
# LISTEN 状态下：Recv-Q = 当前 accept 队列长度，Send-Q = backlog 上限

如果 Recv-Q 长期接近 Send-Q，说明应用 accept 不及时，先调应用或 somaxconn，而不是只加大 tcp_max_syn_backlog。内核计数器也能佐证：

nstat -az TcpExtListenOverflows TcpExtListenDrops TcpExtSyncookiesSent

三、内存与缓冲区

快照值：

tcp_rmem = 4096 131072 6291456      # 4 KiB / 128 KiB / 6 MiB
tcp_wmem = 4096 16384 4194304       # 4 KiB / 16 KiB / 4 MiB
tcp_mem  = 310098 413466 620196     # 页数，约 1.18 / 1.58 / 2.37 GiB
  • tcp_mem：TCP 全局内存页数阈值（min / pressure / max），由内核按系统内存自动计算。超过 pressure 进入内存压力模式，低于 min 退出。
  • tcp_moderate_rcvbuf = 1：接收缓冲区自动调优开关。
  • tcp_notsent_lowat = 4294967295：未发送数据低水位线取 UINT_MAX，等于不限。调低可以让 poll() 更早报告可写、降低写侧排队延迟，但可能牺牲单流吞吐。

三元值的含义

tcp_rmem / tcp_wmem 的三个值分别是最小 / 默认 / 最大：

  • 最小值：内存紧张时每个连接也能保证拿到的额度，不能低于 4096。
  • 默认值：连接建立时的初始缓冲区，也是自动调优的起点。
  • 最大值：自动调优的天花板。接收侧直接决定能通告多大的窗口。

自动调优的实际行为：

  • 接收侧：内核跟踪应用在每个 RTT 里读走的数据量，把缓冲区向"约两倍的每 RTT 消费量"扩充，上限 tcp_rmem[2]。应用读得越快，窗口涨得越大。当前上限 6 MiB，在高速长肥管道上能撑起更大的接收窗口。
  • 发送侧：缓冲区存放已写入但未被确认的数据，自动调优会随 cwnd/MSS 需求增长，上限 tcp_wmem[2]。缓冲区满时 write()/send() 会阻塞或部分写入。

两个容易踩的坑：

  1. setsockopt(SO_RCVBUF/SO_SNDBUF) 会关闭该 socket 的自动调优，此后 sysctl 的最大值对它无效。应用自己设了固定缓冲区，就别再指望内核帮忙扩。
  2. 收发缓冲区是按连接算的。tcp_rmem[2] = 6 MiB 乘以并发连接数才是潜在内存占用，tcp_mem 就是给这堆连接兜底的总闸。

四、重传与超时

  • tcp_retries2 = 15：已建立连接在 RTO 重传失败 15 次后放弃，累计超时约 924 秒（约 15 分钟）。死连接可能占资源到这一刻。

  • tcp_fin_timeout = 60：孤儿连接停留在 FIN_WAIT_2 的超时秒数。

  • tcp_orphan_retries = 0：这里最容易误解。内核源码里 tcp_orphan_retries() 的逻辑是：

    • socket 最近还发过东西（alive）时，0 会被替换成 8 次；
    • socket 已经不活跃时保持 0，也就是尽快放弃；
    • 收到过软 ICMP 错误时也会置 0。

    所以它不是简单的"零次重传"，也不是固定的"默认 8 次"，而是按连接活跃度决定。

  • tcp_rto_min_us = 200000：最小 RTO 200 ms。广域网下是保守合理的值；低延迟数据中心可以评估调小（路由和 socket 选项的优先级高于此 sysctl）。

五、SACK 与时间戳

  • tcp_sack = 1 / tcp_dsack = 1：选择性确认。发送方能精确知道哪些段丢了、哪些只是乱序，多丢包场景的恢复效率远高于累计 ACK。
  • tcp_timestamps = 1：RFC 1323 时间戳，用于 RTT 测量和 PAWS，也是 tcp_tw_reuse 能安全工作的前提。值 2 表示启用但不加随机偏移（一般不这么用）。
  • tcp_comp_sack_nr = 44 / tcp_comp_sack_delay_ns = 1000000：SACK 压缩，最多合并 44 个 SACK，最多延迟 1 ms。目的是减少小包和 ACK 风暴，默认值通常不用动。

六、TIME_WAIT 与端口复用

  • tcp_tw_reuse = 2：这里和网上很多说法相反——2 不是"更安全的全局复用"，而是只对 loopback 流量生效。内核文档写得很清楚：

    值含义
    0禁用
    1全局启用
    2仅 loopback（默认）

    快照里的 2 就是内核默认值。它对本机回环上的代理/转发（比如 sing-box 的本地入站）有用，对"服务端主动连出去耗尽端口"没有帮助。真要在出站方向复用 TIME_WAIT，需要设 1，并且依赖时间戳（PAWS）保证旧连接的迟到报文不会污染新连接。较新内核还增加了 tcp_tw_reuse_delay（默认 1000 ms），控制 TIME_WAIT 套接字至少存活多久才可被复用。

  • tcp_max_tw_buckets = 131072：全系统 TIME_WAIT 套接字上限，超过后新的 TIME_WAIT 直接被销毁并打印警告。它只是防 DoS 的天花板，不应为了"消掉 TIME_WAIT"而调低。

七、其他参数

参数快照值含义
tcp_max_orphans131072无用户进程关联的孤儿套接字上限
tcp_limit_output_bytes1048576每 socket 允许滞留在 qdisc/设备队列的未确认字节，限制本地 bufferbloat；内核新默认值是 4 MiB，这里 1 MiB 更激进
tcp_no_metrics_save0关闭连接时保存 cwnd/rtt 等指标，供后续同目标连接复用
tcp_mtu_probing0关闭 PLPMTUD。存在 ICMP 被阻断的 MTU 黑洞时，设为 1（检测到黑洞才探测）或 2（始终探测）
tcp_fastopen_key6d5b...TFO Cookie 的主密钥（可带一个备份密钥），泄露等于允许伪造 Cookie，日志里应打码

八、专题：ECN 是什么

ECN（Explicit Congestion Notification，显式拥塞通知） 让路由器在队列将满、但还没满时，直接在 IP 头里打标记，提前通知发送方降速，而不是等溢出后丢包。

传统 Reno/CUBIC 只有"丢包"这一个拥塞信号：队列必须先被填满、溢出、丢包，发送方看到重传超时或重复 ACK 才退让。代价是重传延迟，以及 queue 被反复填满带来的 bufferbloat。

ECN 的流程：

  1. 两端在 SYN/SYN-ACK 的 TCP 标志位（ECE/CWR）里协商 ECN 能力；协商成功后，数据包的 IP 头 ECN 字段置为 ECT(0) 或 ECT(1)。
  2. 路径上的 AQM（RED、CoDel、fq_codel 的 ecn 模式等）发现队列超阈值时，把 ECN 字段改成 CE（Congestion Experienced，11），包仍然照常转发。
  3. 接收方看到 CE，在 TCP 头里置 ECE 位回给发送方。
  4. 发送方收到 ECE，像收到拥塞信号一样降速，并置 CWR 位确认；被标记的包已经到达，不需要重传。

IP 头里 ECN 占 2 bit：00 Not-ECT、01 ECT(1)、10 ECT(0)、11 CE。注意 ECN 是"端到端协商 + 路径设备标记"，只在端主机上设置 tcp_ecn 并不会凭空产生 CE 标记——如果路径上的 qdisc 从不做 ECN 标记（例如普通 pfifo_fast），ECN 协商成功也不会带来任何降速收益。

回到 tcp_ecn = 2：作为服务端，它愿意配合入站连接使用 ECN；作为客户端主动连别人时不请求。这个组合在"我的服务器是接收方、对端和路径都支持 ECN"时能减少丢包，同时避免主动连接时与老旧中间设备发生兼容问题。

一个容易忽略的点：BBRv1 不把 ECN 标记作为带宽模型的输入。CE 只通过 TCP 通用的 cwnd 减小流程短暂影响在途窗口，真正决定速率的是 pacing rate；BBRv2/v3 才把 ECN 纳入拥塞响应。所以在 BBR + ECN 的组合里，别期待 ECN 会像对 CUBIC 那样直接改变发送速率。

总结

这份配置的核心特征是：BBR + 默认的 ECN 服务端策略 + SYN Cookie 兜底 + 偏宽松的缓冲区 + 标准重传参数，没有明显激进项。

几个可以按场景复查的点：

  • tcp_tw_reuse = 2 是默认值，只惠及 loopback。出站端口压力大的机器应评估改成 1。
  • tcp_limit_output_bytes = 1 MiB 小于新内核默认的 4 MiB，对延迟友好；但如果单流速率极高（数十 Gbps），需要确认它没有成为本地队列瓶颈。
  • 长肥管道上若单流吞吐上不去，先看接收窗口是否被 tcp_rmem[2] 卡住，以及应用是否用 SO_RCVBUF 关掉了自动调优。
  • 延迟敏感服务可以评估 tcp_slow_start_after_idle=0，但要接受空闲后突发可能造成的排队。
