根分区只读了 23 天才发现：周一凌晨的 fstrim、一块 SMART 全绿的 SSD 和 ext4 损坏排查记

十一月 18, 2026 [Linux 与系统] #Linux #systemd #存储与文件系统 #bmc #serial

根分区只读了 23 天才发现：周一凌晨的 fstrim、一块 SMART 全绿的 SSD 和 ext4 损坏排查记

现象

给一台 ARM 架构的推理服务器跑 apt update，每个源以两种姿势死掉：

错误:1 http://ports.ubuntu.com/ubuntu-ports jammy InRelease
  Couldn't create temporary file /tmp/apt.conf.AN08wd for passing config to apt-key
错误:5 http://ports.ubuntu.com/ubuntu-ports jammy-updates Release
  Could not open file /var/lib/apt/lists/partial/... - open (30: Read-only file system)
W: chown to _apt:root of directory /var/lib/apt/lists/partial failed - SetupAPTPartialDirectory (30: Read-only file system)

两个关键细节：

  1. 连 /tmp 都建不了临时文件——这不是 apt 或镜像源的问题；
  2. errno 30（EROFS）铺满了 /tmp、/var/lib/apt、/var/cache/apt 所有写路径——这不是「某目录权限不对」，是整条挂载链不可写。

顺带发现 14 个 systemd 单元集体 failed（snapd、logrotate、man-db、motd-news、apt-daily……全是写盘的），/var/log/syslog 的修改时间冻结在三个多星期前。

定性：三十秒排除掉四个错误方向

多路径 EROFS 的正确第一反应是看挂载，不是修 apt：

findmnt -n /                        # /dev/sda2 ext4  ro,relatime   ← 实锤
cat /etc/fstab                      # / 挂的是 defaults，排除配置手滑
df -h /                             # 29% 使用，排除磁盘满
sudo blockdev --getro /dev/sda2     # 0，排除设备层写保护

根分区被以只读挂载、fstab 又没这么写，只有一种常见可能：ext4 自己检测到文件系统错误，按超级块里的 errors=remount-ro 策略把根分区保护起来了。剩下的问题只有一个——它看到了什么错误？

取证：内核日志把「谁先动手」钉死了

这台机器的 /var/log/kern.log 恰好从事发前 2 分钟开始（早前内容已轮转），完整保留了案发过程：

时间（某周一凌晨）内核记录
00:15:29–00:16:13sd 1:0:6:0: [sda] tag#… BRCM Debug mfi stat 0x2d, data len requested/completed 0x1000/0x0 ×3
00:17:31tag#983 FAILED … cmd_age=77s，CDB: Unmap…（TRIM/UNMAP 挂了 77 秒后失败）
00:17:31tag#984 Sense Key: Aborted Command，CDB: Write(10) → blk_update_request: I/O error → Aborting journal on device sda2-8
00:18:49 / 00:20:07再两轮 UNMAP + Write 失败，I/O error while writing superblock
00:21:24EXT4-fs (sda2): Remounting filesystem read-only

注意因果顺序：先是盘/链路拒绝服务（TRIM 失败、写命令被中止），然后才是 ext4 受损——不是文件系统自己坏了。

接着对齐「谁在 00:15 开始干活」。这台机器开着 Ubuntu 默认的 fstrim.timer（每周一 00:00 起半小时窗口内跑一次全盘 TRIM）：

10-19 00:44  fstrim 正常完成（trim 78.5 GiB）
本周一 00:14:53  fstrim 启动          ← 与首个 RAID 卡异常只差 36 秒
本周一 00:21:39  fstrim 结束（自称 trim 261.5 GiB，是上周的 3.3 倍）

时间轴严丝合缝。而 e2fsck -n（只读体检）也交出了损伤清单：块位图和 inode 位图几十段不一致、containerd 快照里的证书 symlink inode 类型损坏、甚至有一个日志文件在磁盘上的 inode 被清零（size=0、无数据块，tail 还能读到内容纯粹是因为数据还躺在内存页缓存里——rsyslog 打开它的文件偏移量停在冻结时刻，一字节都没多写）。

为什么是一块「SMART 全绿」的盘？

盘的拓扑（lsblk -f + readlink /sys/block/sda）：

04:00.0 RAID bus controller: Broadcom/LSI MegaRAID Tri-Mode SAS3408
sda → target 1:0:6  型号 ATA / Samsung SSD 870   ← JBOD 直通（所以能看到真实型号）
sdb → target 1:2:0  型号 AVAGO / MR9440-8i       ← 卡上建的真 RAID 逻辑卷（数据盘）

根分区没有 RAID：那是一块 Samsung 870 SATA SSD 以 JBOD 直通挂在 SAS3408 卡后——但「直通」不等于「绕过卡」，I/O 依然穿过 RAID 卡固件（BRCM ... mfi 报错就是驱动与固件之间通信异常）。

事后 SMART 检查：PASSED，Reallocated=0、Reported_Uncorrect=0、UDMA_CRC_Error=0。全绿，但它在事发当晚锁死了 77 秒、中止了写命令、并且丢失了此前已确认写入的数据（那个被清零的 inode 就是「曾被告知写入成功、盘上却没有」的直接证据）。

结论：不是坏块劣化，是「固件/直通通路在 TRIM 压力下的瞬时锁死」。SATA SSD 挂 LSI/Broadcom 卡跑 TRIM 出问题，是有相当先例的坑区。

修复：卡在 initramfs 的那两个小时

文件系统元数据已经不一致，在线 remount,rw 只是掩耳盗铃，必须离线 fsck。流程：

  1. 优雅停掉机器上的虚拟机和容器（VM 磁盘镜像在数据盘，不受影响），把 VM 定义、容器 inspect、/etc、包列表备份到数据盘；
  2. 重启。initramfs 里的 fsck.ext4 -a 撞上 UNEXPECTED INCONSISTENCY; RUN fsck MANUALLY（exit 4），按设计掉进 BusyBox shell 等人工介入；
  3. 然后是本次事故最有教育意义的两个小时（见下一节）；
  4. fsck -y /dev/sda2 跑两遍：第一遍大量 Fix? yes + FILE SYSTEM WAS MODIFIED；第二遍 clean 零修复项才算收工。只跑一遍就收工是常见错误——第一遍的修复本身可能引入新的不一致，第二遍干净是验收标准；
  5. exit 继续启动，确认 / 变回 rw 后，第一件事禁掉 fstrim 定时器——否则下周一它还会来一次。
systemctl disable --now fstrim.timer

教育意义的两个小时：SOL 和 KVM 不是一回事

机器没接显示器，远程修复靠 BMC（这台是华为 iBMC）。它有两条独立的远程控制台通道，我一开始用错了：

通道控制的对象本机表现
SOL（Serial Over LAN，SSH CLI 里 ipmcset -t sol -d activate -v 1 0）物理串口全程零回显，敲进去的字石沉大海
Web KVM（浏览器里的 H5 虚拟控制台）VGA 显示器 + USB 键鼠initramfs 提示符就在这里

差别的根源是内核参数的顺序规则：

console=ttyS0,115200 console=tty0
                          ^^^^^^^^ 排最后的 console= 才是 /dev/console 的输入源

console= 的语义是：输出广播给列表里所有终端，输入只从最后一个读。这台机器把 tty0（VGA）排在最后，所以 initramfs 的 shell 读的是 KVM 键盘；SOL 连的串口上既没有 getty 也没有 shell 在读，我的 fsck 命令全部石沉大海——而且因为 SOL 里全程零回显、零输出，我一度还以为连接没建立。

最终修复就是在 Web KVM 的画面上手敲 fsck -y /dev/sda2。顺便把这条规则记牢：

console= 输出广播、输入单选（最后一个生效）。 想让串口可以敲命令，串口必须排在参数列表最后。

一个页缓存造成的「灵异现象」

排查中有个困惑了很久的矛盾：kern.log 的 mtime 冻结在事发时刻，stat 也是，但 tail 却能读到事发之后日期的内容。真相是：磁盘上的 inode 已被清零（debugfs 直读 size=0），文件在 VFS 层的 14667 字节内容全是只读挂载前残留在页缓存里的数据——tail 读的是内存不是盘。遇到「文件内容比 mtime 新」这种物理矛盾时，先怀疑文件系统本身已经损坏，别急着解释时间线。

加固：让下一次不用蹲浏览器

这次修复能完成，全靠浏览器里的 Web KVM。事后把远程救援能力配齐：

dropbear-initramfs——把一个微型 SSH server 和公钥打进 initramfs 镜像。下次卡在 initramfs 时直接：

ssh root@<服务器内网IP>     # 进入 initramfs 的 busybox shell
fsck -y /dev/sda2
exit

几个只有踩过才知道的点：

  • Ubuntu jammy 的授权文件路径是 /etc/dropbear/initramfs/authorized_keys（老教程写的 /etc/dropbear-initramfs/ 在新版本里不存在）；
  • initramfs 阶段网络要在内核参数里显式给：ip=<机器IP>::<网关>:<掩码>:<主机名>:<网卡>:off；
  • update-initramfs -u 默认只重建最新内核的镜像，机器上还留着旧内核时要用 -k <版本> 逐个补齐，否则回退到旧内核时救援是空的。

console 顺序交换激活 SOL：把参数改成 console=tty0 console=ttyS0,115200（串口排最后），SOL 从「只能看」变成「可以敲」——机器自身网络挂掉时，SSH 到 BMC 的串口就是唯一的键盘。GRUB 菜单不受影响（GRUB 读自己的终端配置），正常启动后 VGA 和串口的 getty 也各自独立。

顺带盘点出的 BMC 通道矩阵，值得抄给每一台有带外管理的机器：

故障深度手段依赖
initramfs 卡住dropbear-initramfs机器自身网络
内核/引导卡死BMC SOL（需 console= 配置）无
图形 / BIOS / 装系统BMC VNC 或 Web KVMVNC 客户端 / 浏览器
需要断电 / 挂 ISOBMC 电源控制 / 虚拟光驱无

总结

  1. 多路径 EROFS（/tmp、/var 同时写不进）= 先 findmnt，别修 apt。报错列表再长，定性只需要一条 mount 信息。
  2. kern.log 里每天重复一条 error count since last fsck: N 是 ext4 定时器在喊「盘上记着错误、等一次 fsck」。看到它就该安排检查，别等 apt 罢工才发现根分区已经只读了 23 天。
  3. SMART 全绿 ≠ 不会锁死。Reallocated/Uncorrect/CRC 全 0 的盘，照样可以整盘锁死 77 秒并丢失「已确认写入」。丢过已确认写入的盘，不应再作为系统盘信任。
  4. 凌晨卡死先对齐 cron/timer：事发时刻（周一 00:15）与 fstrim 定时器（周一 00:00 起的窗口）精确吻合，是把「RAID 卡异常 → ext4 损坏」串成因果链的关键一环。
  5. console= 输出广播、输入单选（最后一个）。SOL 和 KVM 在「内核级输入」上确实是二选一——但可以靠 dropbear-initramfs 把第二把钥匙塞进 initramfs 里。
  6. RAID 卡 JBOD 直通 ≠ 绕过卡：盘还在卡后，固件仍在 I/O 路径上。SATA SSD 挂 LSI/Broadcom 卡跑 TRIM，属于已知坑区。

fstrim 定时器已禁用（对一块只用了 29% 的系统盘，短期不 TRIM 没有可感知的性能代价）；中期计划是把系统盘迁离 RAID 卡（板载 SATA 口可用），之后再恢复定时 TRIM。
