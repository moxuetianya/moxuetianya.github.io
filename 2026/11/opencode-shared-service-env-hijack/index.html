opencode 一夜只剩 4 个模型：共享后台服务被环境变量静默劫持

十一月 18, 2026 [AI] #opencode #agent #llm

现象

某天打开 opencode，模型选择器里只剩 4 个 provider：

$ opencode models
glm/glm-5.3-flash
opencode/beam-free
opencode/big-pickle
...
provider/qwen3.8-27b-fp8
vllm/qwen3.8-27b-fp8

两个疑点：

  1. ~/.local/share/opencode/auth.json 里明明存着 deepseek、智谱、MiniMax、小米的 API key（opencode auth list 全部显示 stored），却一个都不出现——「deepseek 去哪了？」
  2. GLM 只剩 glm-5.3-flash 一个模型，但直接 curl 智谱的 /models 端点明明能拿到全家桶：
$ curl -H "Authorization: Bearer $ZHIPU_TOKEN" \
    https://open.bigmodel.cn/api/coding/paas/v4/models | jq .
# 正常返回 glm-5.3 / glm-5.3-flash / glm-5.3-highspeed ...

接口好的，opencode 却「获取不到」——问题显然不在智谱侧。

排查

第一步：模型列表的来源——opencode 根本不调 /models

opencode 的模型列表来自两个地方，从不请求 provider 的 /models 端点：

  • models.dev 注册表：内置的供应商目录（含 baseURL、模型清单、元数据），定期拉取缓存到 ~/.cache/opencode/models.json；
  • 配置文件里显式声明的 models：自定义 provider 必须逐个写模型条目，写几个显示几个。

所以 curl /models 能拿到什么对 opencode 毫无意义。当前生效的 glm 是个自定义 provider，配置里只声明了 glm-5.3-flash 一个模型——列表里自然只有它。

第二步：生效的配置根本不是 ~/.config/opencode

看运行时 API 问服务端自己认哪些 provider：

$ opencode api get /api/provider | jq -r '.data[].id'
opencode
vllm
glm
provider

正好 4 个，和 opencode models 完全对应。而 ~/.config/opencode/opencode.json 里定义的 local provider 没出现——这份文件根本没被解析。

检查服务进程的环境：

$ pid=$(opencode api get /api/info | jq -r .pid)
$ readlink /proc/$pid/cwd        # /home/peter（不是任何项目目录）
$ tr '\0' '\n' < /proc/$pid/environ | grep -E '^OPENCODE'
OPENCODE_CONFIG_DIR=/home/peter/project/task/.global-opencode
OPENCODE_DISABLE_MODELS_FETCH=1
...

两个关键事实：

  • OPENCODE_CONFIG_DIR 是「替换」语义：设置后 ~/.config/opencode/ 整个目录不再被读，自定义目录顶替它成为全局配置目录。.global-opencode/opencode.jsonc 里有一个 enabled_providers 白名单，只放行了这 4 个 provider——这就是 deepseek 等集体消失的直接原因，key 还存在 auth.json 里也没用。
  • OPENCODE_DISABLE_MODELS_FETCH=1：连 models.dev 注册表都不拉了，模型只能靠配置显式声明。

.global-opencode/ 是 wfuzz agent 平台的会话配置目录（上一篇讲启动排查的文章里已经见过它），每次启动会被整目录重灌，并把平台下发的 model + provider 键合并进 opencode.jsonc——手改这份文件会在下次启动被覆盖。

问题变成了：我在 ~/project/tools 里用的 opencode，为什么会吃 wfuzz 在另一个项目的配置？

第三步：日志里的「静默换服务」

opencode 是客户端-服务端架构：TUI/CLI 连接一个用户级共享单例服务。客户端启动时先做服务发现，规则是——已注册服务健康且版本匹配就附着，否则用客户端自己的二进制和环境拉起一个新服务（daemon 化、接管注册表）。

在 ~/.local/share/opencode/log/opencode.log 里搜服务更替事件：

$ grep -a 'background service starting' ~/.local/share/opencode/log/opencode.log | tail -5
2026-11-13T08:28:14 ... reason=version-mismatch previousVersion=2.2.7
2026-11-13T08:57:27 ... reason=version-mismatch previousVersion=2.0.7
2026-11-17T07:24:18 ... reason=version-mismatch previousVersion=2.2.7
2026-11-17T08:54:02 ... reason=version-mismatch previousVersion=2.0.7

版本在 2.2.7 ↔ 2.0.7 之间打乒乓——谁后跑，谁就把单例服务换成自己的版本 + 自己的环境。

2.0.7 是哪来的？wfuzz agent 的下载缓存里有答案：

$ ls ~/.wfuzz/<server>/wfuzz-agent/
0_1_46 ... 0_2_0  0_2_1  0_2_3
$ ~/.wfuzz/<server>/wfuzz-agent/0_2_3/bin/opencode --version
opencode v2.0.7      # 0.1.x 系列甚至还是 1.17/1.18

wfuzz 捆绑的 opencode 是 2.0.7，系统里的是 2.2.7。每次 wfuzz 会话启动，它的 2.0.7 客户端发现注册的服务版本不匹配 → 拉起新服务（继承 wfuzz 注入的 OPENCODE_CONFIG_DIR 等环境）；之后任何一次系统 2.2.7 的运行又把它换回来。

第四步：为什么「我什么都没做」配置却变了

时间线精确到秒：

时刻事件
11-17 16:54:02一个客户端报告 version-mismatch previousVersion=2.0.7，拉起新服务
11-17 16:54:03新服务 PID 2699039 daemon 化（ppid=1）
同一秒wfuzz 重灌 .global-opencode/（目录 mtime 全是 16:54）

而这个新服务的诡异之处：二进制是系统 2.2.7（readlink /proc/PID/exe），环境却是 wfuzz 那套（OPENCODE_CONFIG_DIR 等全在 environ 里）。

这推翻了「环境变量残留」的直觉——进程死了环境就没了，环境变量不可能「残留」到下一个进程。新服务的环境是启动它的客户端在 spawn 那一刻注入的快照，「2.2.7 二进制 + wfuzz 环境」说明发起者本身就是这个组合：一次在 wfuzz 注入环境里运行系统 PATH 二进制的调用。版本和环境永远同源，都来自发起替换的那个进程。

这个组合态还是最稳定的坏状态：

  • 如果服务是 2.0.7：日常任何一次 opencode 都会 mismatch 替换它，活不长；
  • 但「2.2.7 + wfuzz 环境」：所有日常客户端版本匹配 → 安静附着、毫无察觉 → 从 11-17 一直稳坐到发现问题时。

版本匹配完美掩盖了环境劫持。

第五步：对照实验——附着客户端的环境变量完全不生效

建一个带独特 provider 的配置目录，用它启动客户端：

$ mkdir -p ~/.tmp/opencode/client-cfg-demo
$ cat > ~/.tmp/opencode/client-cfg-demo/opencode.jsonc <<'EOF'
{ "provider": { "clientonly": {
    "name": "ClientOnlyDemo",
    "npm": "@ai-sdk/openai-compatible",
    "options": { "baseURL": "http://127.0.0.1:9/v1", "apiKey": "demo" },
    "models": { "demo-model": {} } } } }
EOF

$ opencode models                          # A: 正常启动
$ OPENCODE_CONFIG_DIR=~/.tmp/opencode/client-cfg-demo opencode models   # B

A 和 B 输出完全一致，clientonly/demo-model 始终没出现，服务 PID 没变——附着模式下，客户端的 OPENCODE_CONFIG_DIR 对服务端零影响。

机制总结

客户端的环境变量是否生效，取决于这次启动最终附着还是拉起服务：

层级附着已运行服务时由谁决定
服务级：OPENCODE_CONFIG_DIR / OPENCODE_CONFIG、provider key、代理、OPENCODE_DISABLE_MODELS_FETCH❌ 完全无效服务进程出生那一刻的环境，出生后不再重读
会话级：项目配置链（opencode.json(c)、.opencode/、AGENTS.md、skills）✅ 有效客户端把启动时的 cwd 作为会话目录交给服务端，服务端从该目录向上发现
客户端本地：cli.json（主题、按键等终端偏好）✅ 有效客户端进程自己读

配套的还有三条：

  1. 模型列表 = models.dev 注册表 ∪ 配置显式声明，与 provider 的 /models 端点无关；
  2. OPENCODE_CONFIG_DIR 是替换不是叠加，设置后默认目录整个失效；
  3. enabled_providers 是白名单，不在名单里的 provider 即使有凭据也不显示。

修复与建议

对使用者：

# 临时用另一套配置（私有服务，环境百分百生效，不碰共享单例）
opencode --standalone

# 永久切换：新终端里（干净环境）
opencode service stop && opencode service start

对会注入环境的 agent 平台（wfuzz 这类）：

  • 根治：会话用 --standalone 起私有服务，或平台自管服务生命周期（独立端口 + 密码 + 显式连接），不要依赖「碰巧版本不匹配/服务不在场」才注入成功；
  • 防御：exec 之后校验附着到的服务环境里含自己的标记变量（如 WFUZZ_PRODUCT），不含就报错退出，而不是静默跑在裸配置上；
  • 同步升级捆绑的 opencode 版本——版本差本身就是乒乓的源头。

顺带一个命名陷阱：models.dev 里智谱有四个 provider——zhipuai（国内开放平台）、zhipuai-coding-plan（国内 Coding Plan，open.bigmodel.cn/api/coding/...）、zai / zai-coding-plan（海外 Z.AI，api.z.ai）。国内 Coding Plan 的 token 存到 zai-coding-plan 名下会直接 401，登录时认准 "Zhipu AI Coding Plan"。

总结

这次排查最大的收获是把 opencode v2 的配置解析边界搞清楚了：重配置（provider/模型/权限）只在服务进程里解析一次，客户端唯一可靠贡献的是会话目录。一旦理解「附着 vs 拉起」这个分叉，「我什么都没做、配置却全变了」就不再是玄学——一定有一个带着不同环境的客户端，在某次服务不在场或版本不匹配的时刻，悄悄坐上了单例的位置。

排查这类问题的固定三板斧：

pid=$(opencode api get /api/info | jq -r .pid)
tr '\0' '\n' < /proc/$pid/environ | grep -E '^OPENCODE'   # 服务吃的哪套环境
opencode api get /api/provider | jq -r '.data[].id'        # 服务认哪些 provider
grep -a 'background service starting' \
    ~/.local/share/opencode/log/opencode.log               # 服务被谁换过
