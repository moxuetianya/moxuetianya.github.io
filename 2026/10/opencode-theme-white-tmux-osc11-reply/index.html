tmux 里的 opencode 一夜变白：tmux 对 OSC 11 背景色查询的代答

十月 22, 2026 [AI] #opencode #tmux #Terminal

现象

SSH + tmux 环境下（上一篇 OSC52 剪贴板排查 的同款环境），按博客的修法处理完、重新登录之后：

  • 新开的所有 opencode TUI 都是白色背景主题；
  • 之前就在跑的老窗口（同一个 tmux session 的 window 4-7）仍然是暗色；
  • 同一台机器、同一个 ~/.opencode/bin/opencode、同一份 cli.json。

很容易怀疑是博客那三处修改（allow-passthrough on、DISPLAY 改写、tmux extended-keys）干的。最后证明全都无关——根因在 tmux 的一个少有人知的行为：替外层终端代答 pane 的 OSC 10/11 颜色查询。

排查：先排除显然的假设

排查思路是「每个假设配一个可证伪的实验」，全部在同一台机器上完成。

版本假设：二进制在 10-20 升级过（老进程的 /proc/PID/exe 指向 deleted inode）。但用带转义序列的截屏对比各窗口实际渲染的主题：

tmux capture-pane -e -p -t 0:$w | grep -ao '48;2;[0-9;]*' | sort | uniq -c | sort -rn | head -3

window 5/7 与变白的 window 1 跑的是同一个 v2.0.32（窗口背景 10;10;10 暗 vs 255;255;255 白），一暗一白——版本排除。

环境变量假设：老窗口进程的 DISPLAY=localhost:xx + 已死的 waypipe socket，新窗口是 127.0.0.1 + 活 socket。在 tmux 里开新窗口跑全新 opencode 做环境矩阵：完整环境、只 X11、只 Wayland、全剥掉（env -u DISPLAY -u WAYLAND_DISPLAY）——四种全是白主题。环境排除。

tmux 配置假设：allow-passthrough 开/关各跑一次——都是白。且 ~/.tmux.conf 的 mtime 是 10-15，早于翻转点。COLORFGBG、cli.json（mtime 未变）、状态库 kv 表也都没有主题相关的值。全部排除。

决定性实验：抓 opencode stdin 上到底收到了什么

用 script 的双向日志（-O 记输出、-I 记输入），在 tmux pane 里给 opencode 套一层 pty：

script -q -f -O /tmp/oc-out.log -I /tmp/oc-in.log -c opencode

启动几秒后分析，INPUT（到达 opencode stdin 的字节）：

\x1b]10;rgb:0000/0000/0000     ← 前景色：黑
\x1b]11;rgb:ffff/ffff/ffff     ← 背景色：白 ★
\x1b[?1;2;4c                   ← DA1 应答

**OUTPUT（opencode 发出的）**里有 \x1b]10;? / \x1b]11;? 两条查询。也就是说：opencode 启动时问终端「你的默认前景/背景色是什么」，tmux 3.5 直接替外层终端应答了，而且答的是白背景。opencode 拿到 rgb:ffff/ffff/ffff，按亮度判定 light 主题——白色背景就是这么来的。

用一个最小 python 探针（raw 模式发 ESC]11;?ST、select 读 stdin）可随时复现：

raw模式 OSC11 应答: ^[]11;rgb:ffff/ffff/ffff^[\    ← tmux 的代答

探针的坑：最初两轮探测都「无应答」，一度以为 tmux 不代答。其实是 pane shell 的 tty 处于规范模式（ICANON）——OSC 应答里没有换行符，规范模式永远不会把它交付给 read()，select() 也不报可读。必须先用 termios 把 stdin 设成 raw（至少清掉 ICANON）才能收到。opencode 自己就是 raw 模式，所以它一直收得到。

因果链与时间线

opencode 默认 theme.mode = "system"
  └─ 启动时发 OSC 10/11 颜色查询
      └─ tmux 3.5 替外层终端代答（attach 时用 ccolour 机制问真实终端并缓存）
          └─ 当前缓存/回落的背景色 = rgb:ffff/ffff/ffff（白）
              └─ opencode 判定 light → 白色主题

tmux 的代答值什么时候变的？对齐进程启动时间：

  • 14:51:04 从 kitty 重新登录 attach（tmux a，pts/0，TERM=xterm-kitty）；
  • 14:51:18 启动的 opencode → 白（attach 后 14 秒）；
  • 14:37:27 启动的 opencode（此时 kitty 尚未 attach）→ 暗色；
  • 更早的窗口 4-7 → 暗色，且主题在启动时定死、不随后续变化。

即代答变白与「kitty client attach」精确同步。至于是本地 kitty 上报了浅色背景、还是 kitty 没有应答 tmux 的颜色查询导致回落到 xterm 经典默认（白底黑字），取决于本地终端配置，没有再深究——因为修法与它无关。另外当时还有第二个 client（昨晚 attach 的 TERM=xterm-256color 终端）挂在同一个 session 上，多 client 时 tmux 用哪个 client 的颜色也不确定；同一场里 Shift+Enter 失效也是这个「双登录并存」引起的（extkeys 特性只授予了 xterm-kitty 的 client），一并退出旧登录即可。

修复

主题固定为暗色，与 tmux 代答什么彻底脱钩。~/.config/opencode/cli.json：

{
  "theme": { "name": "opencode", "mode": "dark" }
}

或者在 TUI 里 /settings → Appearance → Color mode → dark mode。改完重开 opencode 生效。

总结

  • 「system」主题的 TUI 本质上是问终端要背景色；在 tmux 里，回答问题的不是你的真实终端，而是 tmux 的代答（ccolour 缓存，可能过期、可能回落到白底黑字的经典默认、多 client 时还可能换人）——颜色查询和 OSC52 一样是「跨终端边界会被中间人改写」的链路。
  • 排查这类问题的两个趁手工具：script -O/-I 双向日志（看程序真实收到/发出的转义序列），和 raw 模式 + select 的最小探针（随时复问 tmux）。注意 pane 里的 tty 默认是规范模式，探针必须先关 ICANON，否则无换行的应答永远读不到——这个坑本身比结论更值得记住。
