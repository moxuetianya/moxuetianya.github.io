PVE 虚拟机每 35 秒卡 3 秒：一场从 ping 到 btrfs log commit 的排查

十月 30, 2026 [虚拟化与容器] #存储与文件系统 #虚拟化 #调试 #qemu

现象

一台跑在 Proxmox 上的开发虚机（下称 vm-a，16 vCPU / 32G / virtio-scsi 单盘 300G，iothread=1、cache=none），用起来有这样的体感：

  • ssh 登录经常要顿一下才出提示符；
  • 在里面敲命令，偶尔一个再普通不过的命令（比如 jobs）也要卡几秒，然后突然一口气全出来；
  • 同一宿主上另一台虚机 vm-b「没有这个问题」。

宿主是一台 Proxmox 节点，数据盘是一块 62.9T 的 MegaRAID 阵列，上面一个 btrfs 文件系统挂了四个子卷给 pvesm 当存储（images 都在里面，raw 格式）。

第一步：先排除「显而易见」的（这一步基本都在走弯路）

把能想到的都测了一遍，结论都是「不是它」：

怀疑对象实测结论
网络平时 ping 0.3ms；卡顿时出现 2640→2434→2225→…→146ms 的等差衰减（步长正好等于 ping 间隔 0.2s），零丢包像是「整条路冻住再一次性放行」，先记着
bufferbloat拉 300MB（539Mbps）期间 ping 最大 1.0ms不是
CPU 抢占guest 内 %steal 全程 0，宿主 256 核基本空闲不是
磁盘带宽dd oflag=dsync 150MB 只要 105ms空闲时盘很快
sshd / shellzsh -i -c jobs 温热 45ms；ICMP 也卡不是
gpg-agent每次公钥签名 440ms（同 key 走 OpenSSH ssh-agent 只要 0.6ms）真问题，但只解释登录慢 0.8s，解释不了「几秒」
sshd PerSourcePenaltiesOpenSSH 10.2 默认开启，一次未认证连接就让整个源 IP 被封 15–600s真问题，但表现为「连接被重置」而不是「卡几秒」

弯路记录：那条等差衰减的 ping 曲线一开始被我当成「网络层冻结」的证据，还推导过「qemu 块设备线程卡住拖累主循环导致网络停」。后来双机对照 + 全程 ping 监控证明：卡顿发生时 ping 一直是 0.4ms，网络从头到尾是无辜的。衰减曲线其实是「宿主把发往虚机的 ICMP 缓在 tap 里，I/O 一恢复就批量放行」的表现——根因还是在存储，只是当时把因果弄反了。

第二步：双机对照，一发命中

写了一个几十行的探针，同时扔到同宿主的两台虚机里：每 5 秒做一次「写 4KB + fsync」（注意写到磁盘路径而不是 tmpfs！第一版写在 /tmp 上，而 vm-a 的 /tmp 是 tmpfs，探针完全测不到盘），记录每次延迟：

== vm-a: fsync 样本 62  p50=3.2ms  p95=970.8ms  max=1888ms
   >100ms: 17:22:44 1888 / 17:23:58 429 / 17:24:34 1363 / 17:25:09 1732 / 17:25:44 971 / 17:26:18 562
== vm-b: fsync 样本 62  p50=2.1ms  p95=1964.8ms  max=2887ms
   >100ms: 17:22:44 2887 / 17:23:58 1427 / 17:24:34 2362 / 17:25:09 2722 / 17:25:44 1965 / 17:26:18 1558

三个信息量爆炸的细节：

  1. 两台虚机在同一秒卡（17:22:44、17:23:58、17:24:34…完全对齐）；
  2. 两台的差值恒等于 ~1.0s——就是两个探针的采样相位差，说明它们在同一时刻被放行；
  3. 卡顿间隔稳定在 ~35 秒（72.5 / 36.9 / 35.4 / 34.2 / 33.6 / 33.9，其中 72.5 是漏采一次）。

结论：这不是某台虚机的问题，是宿主共享层（存储）每 35 秒冻 1–3 秒。vm-b 之所以「没问题」，只是因为它空着没人用。

顺带用 bpftrace 在 vm-a 里抓到了同步证据——ext4 日志线程在等块设备：

17:15:36 DSTATE 1966ms comm=jbd2/sda2-8 pid=373

io_schedule+76
bit_wait_io+17 → __wait_on_bit → __wait_on_buffer
jbd2_journal_commit_transaction+4778
kjournald2+163

（期间还抓到 runc 每次阻塞 2–3 秒，栈是 rwsem_down_read_slowpath → exec_mmap / __vma_start_write，那是 podman healthcheck 的 mmap_lock 争用，与本案无关，别被带偏。）

第三步：上宿主，栈直接把机制钉死

宿主 dmesg 里有一天前的 hung task（>122 秒）：

task:iou-wrk-4217  state:D
  wait_log_commit+0x94/0x100        [btrfs]
  btrfs_sync_log+0x982/0xc60        [btrfs]
  btrfs_sync_file+0x4d1/0x680       [btrfs]
  vfs_fsync_range+0x4b/0xa0
  io_fsync+0x3d/0x60                 ← qemu（aio=io_uring）发来的 fsync
  io_issue_sqe → io_wq_submit_work → io_wq_worker

同一时刻一堆任务全栈在 wait_log_commit，另外还有 btrfs_commit_transaction。而 megaraid 驱动零 sense/abort/reset、零 I/O error，iostat 里阵列写入 4400+ IOPS、w_await 0.2ms、%util 15%——阵列又快又健康。

再看 btrfs 状态，真正的根因出来了：

Device size:        62.87 TiB
Device allocated:   62.87 TiB
Device unallocated:  1.03 MiB     ← chunk 已经分配光
Data, single:  total 62.57TiB  used 54.81TiB   (87.5%)
Metadata, DUP: total   156GiB  used 113.99GiB  (73%)
Free (statfs): 7.76 TiB                  ← 有空间，但全在已分配的 chunk 里
[/dev/sda1].corruption_errs  32379       ← 另一个必须处理的完整性问题

根因

把链路串起来：

guest 写 + flush（cache=none，每次 flush 都落到宿主）
  → qemu（io_uring）对 raw 文件发 io_fsync
    → btrfs_sync_file → btrfs_sync_log → wait_log_commit
       └─ btrfs 的 transaction / log commit 是【全局串行】的：
          一次提交期间，这个文件系统上所有 fsync 排队等它

而这个 btrfs chunk 已分配光（unallocated ≈ 1MB）、用到 87.5%，写路径上的元数据预留会退化成 flush_space(COMMIT_TRANS)——同步触发一次全局事务提交；提交本身又因为空间紧张而变慢。默认 commit=30s 的定时提交叠加这条路径，就得到精确的「每 ~35 秒一次，全存储上的虚机一起冻 1–3 秒」，极端时就是 dmesg 里那次 122 秒。

处置（按风险从低到高）

# ① 秒级可回滚：把提交间隔 30s 拉到 120s，尖峰次数直接降到 1/4
mount -o remount,commit=120 /home
# 验证：guest 探针里卡顿间隔应从 ~35s 变成 ~123s —— 也是最终定案的判据

# ② 若开了 qgroup 就关掉（每次 commit 遍历 qgroup，是提交变慢的经典元凶）
btrfs quota status /home && btrfs quota disable /home

# ③ 腾空间 + 只搬低利用率 chunk，让 unallocated 回到几十 GB
#    （千万别做全量 balance，55T 会跑好几天）
btrfs balance start -musage=50 /home &
btrfs balance start -dusage=40 /home &

# ④ 虚机盘改 cache=writeback，减少触发点（需 stop→start，注意保留 iothread 等参数）
cur=$(qm config 101 | awk -F': ' '/^scsi0:/{print $2}' | sed 's/,cache=[^,]*//g')
qm set 101 --scsi0 "${cur},cache=writeback"

长期方案：这块阵列既然健康，VM 盘值得挪去 LVM-thin（同阵列切 LV，没有 log commit 这个放大器）；btrfs 留给备份、ISO 这类不依赖 fsync 的数据。另外 corruption_errs 32379 是独立的数据完整性问题，性能修完仍要 scrub + 查内存/RAID cache。

总结

这次能收敛，靠的是三件事，比结论本身更值得复用：

  1. 找一个对照组。两台同宿主虚机跑同一份探针，「同秒冻结 + 恒定相位差」两个特征直接把问题从虚机层踢到宿主共享层，比任何单机数据都有说服力。
  2. eBPF 抓栈，不要猜。bpftrace 在 guest 里 20 行脚本就拿到 jbd2 → io_schedule → __wait_on_buffer，在宿主上 dmesg 的 wait_log_commit 栈把最后一环补齐。猜「网络冻结」的那一版解释就是没有栈的时代产物。
  3. 周期是极强的指纹。35 秒 ≈ btrfs 默认 commit=30 + 提交耗时；改一个参数让周期变成 123 秒，因果就闭合了。遇到「间歇性卡顿」先想办法测出它的周期，往往离答案就不远了。

顺带捞到的两个真问题也值得记着：OpenSSH 10.2 默认开启的 PerSourcePenalties 会在单用户内网里因为一次失败把整 IP 封 15 秒以上（表现为 kex_exchange_identification: Connection reset 或服务端横幅 Not allowed at this time，单人内网建议 PerSourcePenalties no）；以及 gpg-agent 替 ssh 签名每次 ~440ms（raw PKSIGN 同样慢，换 OpenSSH ssh-agent 是 0.6ms），这是「每次登录都顿一下」的固定成本。
