virt-viewer 黑屏：spice-gtk 0.42 与 QEMU 10 的 GL dmabuf 不兼容排查

十月 18, 2026 [虚拟化与容器] #qemu #调试

现象

2026-10-18 把日常开发机 VM 从 ubuntu.code 改名为 ubuntu（连同磁盘文件、外部快照 overlay、快照元数据一起改——改名流程本身另有一套坑，改完重启 VM 想开 console 看看，结果：

  • virt-viewer 窗口能开、能连，但永远黑屏；
  • 窗口中央一直挂着「已连接到图形服务器」的占位文案；
  • 右缘偶尔出现红色渲染残条。

时间点太巧了——刚改完名就坏，第一反应当然是「是不是改名改坏了」。这篇记录的是怎么把改名这个头号嫌疑人排除，并一路挖到真正根因的全过程。

环境：Debian trixie（libvirt 11.3 monolithic + QEMU 10.0.6 + spice-server 0.15.2 + spice-gtk 0.42 + virt-viewer 11.0，Intel RPL-S 核显 / Mesa 25.0.7）；VM 为 Ubuntu 22.04 桌面，virtio-vga-gl + spice + gl=on + unix socket 监听。

第一轮：先排除「服务器没画面」

按「先看远端有没有内容，再看链路」的顺序，服务器侧一路正常：

$ virsh -c qemu:///system domdisplay ubuntu
spice+unix:///var/lib/libvirt/qemu/domain-1-ubuntu/spice.sock

$ virsh -c qemu:///system dumpxml ubuntu | grep -A5 '<graphics'
    <graphics type='spice'>
      <listen type='socket' socket='/var/lib/libvirt/qemu/domain-1-ubuntu/spice.sock'/>
      <image compression='off'/>
      <gl enable='yes' rendernode='/dev/dri/renderD128'/>
    </graphics>

$ virsh -c qemu:///system qemu-agent-command ubuntu '{"execute":"guest-ping"}'
{"return":{}}
  • 图形设备在通告、socket 文件存在、目录权限正常（用户已加入 libvirt-qemu 组）；
  • guest agent 应答；ssh 进 guest 看 loginctl list-sessions / ps：GDM + gnome-shell 都在跑，/dev/dri/card1 + renderD128 正常——「虚拟机没开 GUI」的猜测排除；
  • /var/log/libvirt/qemu/ubuntu.log 里 spice 以 gl=on,rendernode=... 正常启动，只有若干 vrend_* 噪音（guest 内 gstreamer 扫描 GL 的报错，反而证明 virgl 渲染管线活着）。

最意外的是 virsh screenshot 竟然成功了：

$ virsh -c qemu:///system screenshot ubuntu /tmp/screen.ppm
截屏保存为 /tmp/screen.ppm，类型为 image/png。

$ identify -verbose /tmp/screen.ppm | grep -E 'mean|standard deviation'
      mean: 0.113555        # 1280x800，均值 ≈29/255
      standard deviation: 4.39

（我自己的旧笔记里还记着「virgl 之后 virsh screenshot 失效」，qemu 10 已经能对 GL scanout 做 screendump 了。）截图像素分析显示：不是纯黑，是被调暗的 GDM 登录屏——服务器侧有真实画面，问题在客户端渲染链路。

第二轮：virt-viewer debug 日志——一个真问题，但不是根因

要拿客户端日志，先踩了三个坑：

  1. virt-viewer --debug 默认一行都不输出：GLib 的 g_debug 需要 G_MESSAGES_DEBUG=all 才启用；
  2. 输出重定向到文件后 stdout 是全缓冲，timeout 一杀进程，日志全部丢失——用 stdbuf -oL 或者干脆别重定向；
  3. virt-viewer/remote-viewer 是 GApplication 单实例：已经开着一个窗口时再启动，只会「唤醒」旧实例然后零输出退出（这就是我第一次抓到 0 行日志的原因）。

拿到日志后，关键段落：

virt-viewer-DEBUG: Guest ubuntu has a spice display
virt-viewer-DEBUG: Set connect info: localhost,localhost,-1,-1,(null),/var/lib/libvirt/qemu/domain-1-ubuntu/spice.sock,(null),-1
virt-viewer-DEBUG: Error 禁止操作：只读访问阻断 virDomainOpenGraphicsFD
virt-viewer-DEBUG: After open connection callback fd=-1
virt-viewer-DEBUG: Opening direct UNIX connection to display at /var/lib/libvirt/qemu/domain-1-ubuntu/spice.sock

机制：virt-viewer 用只读 libvirt 连接查域名与图形地址（只读够用），然后对每个 spice 通道调 virDomainOpenGraphicsFD 要 fd——新版 libvirt 按安全加固在只读连接上拒绝这个调用（fd 传递等于写级权限）。更糟的是 virt-viewer 11.0 只有主通道失败后有「direct UNIX connection」回退；G_MESSAGES_DEBUG=all 日志里 display/cursor/inputs/usbredir 通道拿到 fd=-1 后零 GSocketClient 连接尝试——它们卡死在 open-fd 模式等 fd 喂，display 通道永远不建立。

于是改用 remote-viewer 完全绕开 libvirt fd 通道直连 socket：

remote-viewer "spice+unix:///var/lib/libvirt/qemu/domain-1-ubuntu/spice.sock"

还是黑屏。 通道问题被绕过，但不是根因，继续挖。

第三轮：服务器侧通道核对 + 裸 qemu 对照实验

绕开 libvirt 后，先看服务器侧：这个客户端到底连上了哪些通道？

$ virsh -c qemu:///system qemu-monitor-command ubuntu --hmp 'info spice'
Channel:
     channel: 1:0
     channel name: main
Channel:
     channel: 2:0
     channel name: display          # ← display 通道也连上了
...

8 个 channel 全在（main/display/cursor/inputs/usbredir×2/playback/record）——通道完全不是问题。

那就把 libvirt 和 guest 整个排除掉：起一个无 libvirt、无 guest、无磁盘的裸 qemu，只跑 SeaBIOS，做二分对照：

# gl=on 版
qemu-system-x86_64 -m 256 -spice unix=on,addr=/tmp/test-spice.sock,disable-ticketing=on,gl=on,rendernode=/dev/dri/renderD128 \
  -device virtio-vga-gl -display none -accel tcg -nodefaults -no-user-config

# gl=off 版：只去掉 -spice 的 gl/rendernode 和设备名的 -gl

结果：

  • gl=on 裸 qemu：客户端花屏，画面呈「递归嵌套」纹（其实是 stride/modifier 错配的典型相）；qemu 进程每秒循环刷：

    qemu-system-x86_64: warning: spice: no gl-draw-done within one second
qemu-system-x86_64: warning: console: no gl-unblock within one second

    这是 qemu 的 GL 绘制看门狗：scanout dmabuf 交给 spice-server、客户端收到 GL_DRAW 后必须回执 GL_DRAW_DONE，qemu 才解 block 下一帧。客户端导入失败、不回执 → 每秒超时 → console 永远卡死。

  • gl=off 裸 qemu：BIOS 文字画面完美渲染。非 GL 路径全健康。

第四轮：qemu 自带 GTK 客户端——证明服务器导出无辜

同一个 gl=on 裸 qemu，换客户端：-display gtk,gl=on（qemu 自己经 EGL 导入 dmabuf，不经过 spice 协议）。BIOS 画面完美。

结论落地：

层状态
qemu / virglrenderer 导出 dmabuf✅ 正常（qemu 自带客户端渲染完美）
spice 协议 / 非 GL 路径✅ 正常（gl=off 完美）
spice-gtk 0.42 的 GL dmabuf 导入/渲染❌ 系统级失效

spice-gtk 0.42 是 2022 年发布的上游最后一版（trixie 也停在 0.42-3），拿到 GL_DRAW 后导入 dmabuf 失败（怀疑是 layout/modifier 与 QEMU 10 不匹配），既不渲染也不回执。

「改名嫌疑」是怎么排除的

三组硬证据：

  1. 裸 qemu 复现：它没有 libvirt、没有域名、没有改名、没有 guest，照样花屏 + 看门狗刷屏——改名在物理上影响不到它；
  2. 时间线：last -x reboot 显示 guest 上次开机是 10-13，今天改名重启才第一次用「新 qemu 进程」——不存在「旧进程跑旧状态所以正常」的掩护；
  3. shell 历史（zsh extended history 带时间戳）：10-13 到今天改名前，一次都没启动过 console 查看器——所有 virt-viewer/remote-viewer 记录都是今天 17:27 之后。所谓「改名后坏了」，真实含义是「改名后第一次用才暴露」；实际损坏点更早（2025-12-05 的 qemu/libvirt 升级后的某个时点），改名只是恰好背锅。

解决：回退普通 spice 2D + 恢复 cockpit 图形 console

virgl 在这台机器上的定位本来就有限——它只是 OpenGL 4.3 API 转发，Blender 的 GPU 渲染（CUDA/OptiX）本来就不可能（之前专门做过调研）。而 console 可用性是刚需，于是直接回退：

<!-- 删除 graphics 里的 gl 元素 -->
-      <gl enable='yes' rendernode='/dev/dri/renderD128'/>
<!-- 删除 video 里的 3D 加速 -->
       <model type='virtio' heads='1' primary='yes'>
-        <acceleration accel3d='yes'/>
       </model>

设备从 virtio-vga-gl 退回 virtio-vga，guest 内 GNOME 自动落 llvmpipe 软件渲染，console 立即恢复。

顺带解决了另一件事：2026-09 为开 virgl 被迫把 spice 从 TCP 改成 unix socket（GL 需要 fd 传递，TCP 做不到），而 cockpit-machines 前端只认 <graphics> 上带 port/autoport 属性的监听，导致 cockpit 网页端图形 console 消失、只剩串口（串口里 zsh 彩色 prompt 的 ANSI 转义还会渲染成 K32m 之类乱码）。GL 不需要了，监听改回：

<graphics type='spice' autoport='yes' port='-1'>
  <listen type='address' address='127.0.0.1'/>
  <image compression='off'/>
</graphics>

cockpit 浏览器内图形 console（spice-html5）恢复，virsh domdisplay 返回 spice://127.0.0.1:5900。前因后果见 cockpit-machines 只剩串口 console 那篇。

入口侧也统一了：新增 ~/.my_local/bin/view-vm 脚本，用 virsh domdisplay 拿当前图形 URI 再 remote-viewer 直连，不经 libvirt fd 通道、也不硬编码 socket 路径/端口（autoport 每次可能不同）：

#!/bin/bash
# view-vm [vm名] [libvirt URI]
set -euo pipefail
vm="${1:-ubuntu}"
conn="${2:-qemu:///system}"
uri="$(virsh -c "$conn" domdisplay "$vm")"
exec remote-viewer "$uri"

GNOME 启动器 Exec 用同样逻辑的内联 sh -c，这样无论监听是 socket 还是 TCP、端口怎么变，入口都不用改。

总结

  • 分层对照实验是这次的关键：裸 qemu 排除 libvirt/guest/XML；gl=on vs gl=off 单独拎出 GL 路径；qemu 自带客户端把「导出方 vs 导入方」劈开。每轮只动一个变量，结论就没有歧义。
  • 看门狗日志是金矿：no gl-draw-done within one second 一句话说明「接收方没回执」，比客户端任何日志都直接。qemu 的这类 1 秒超时告警值得养成习惯去搜。
  • 时间线证据要拿硬的：last、shell history 时间戳，比「我记得还能用」可靠得多。
  • 两个独立问题别混成一个：virt-viewer 只读连接被拒 virDomainOpenGraphicsFD（导致通道连不上）是另一个问题，顺手用 domdisplay 直连绕开了；它与 GL 渲染失效叠加，才让现象看起来更像「整个 console 全坏」。
  • 这套栈（QEMU 10 + spice-gtk 0.42）的 GL 兼容性目前无解：spice-gtk 2022 年后无新 release，只能等上游修复或自打补丁。日常用 console 的场景，普通 2D spice 是当下最稳的落点。
