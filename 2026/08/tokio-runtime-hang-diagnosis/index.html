tokio 运行时「睡死」诊断记录：message-queue-enhance 服务异常排查

八月 25, 2026 [rust, debugging] #tokio #debugging #rust #wchan #gdb #core-dump #procfs #ws #troubleshooting

排查/学习路径

一句话结论：一个 tokio+axum 服务在"双隧道并发注册 + 旧对存活"的重叠场景下，registry.insert() 撞上 dashmap 6.2.1 自研写锁的多 writer 丢失唤醒（lock_exclusive_slow），两个以上 worker 永久卡在锁上；恰逢其中一位正持有 tokio io/timer driver 的单 owner 令牌 → epoll 无人轮询 → 其余 worker 无限空闲等唤醒永不满足 → 全 runtime 静默死透（进程活着、端口监听、日志停写、请求无响应）。

学习路径建议（按本文结构，每段可独立跳到）：

  1. 会看症状 → 现象 + 第一步/第二步：TCP 能连 ≠ 服务能用；ss/lsof 谁在听；日志停止点=第一现场
  2. 学会"判定进程是否活着"（活死判定） → 第三步 wchan 全分布（futex_wait_queue vs do_epoll_wait vs park_condvar 的意义）+ 第五步 epoll fdinfo 注册表
  3. 学会取证 → 第四步 gcore → 手工解栈（无 DWARF 时 x/8gx $rsp + nm 基址）→ 带 DWARF 的 debug 版（本项目一键 build 出 .debug，gdb 免参数全栈）
  4. 会复现（可跑通）→ 复现成功 章 + 脚本下载（repro7/8 一键起）→ 三次独立命中；最小独立样本见 最小独立复现样本（按生产锁序的 tokio 版，3/3 命中 lock_exclusive_slow）
  5. 懂根因 → 根因锁定（dashmap 状态机 + 读锁跨 await 红线）→ 连锁反应（driver 令牌断供）
  6. 懂怎么修 → QA 的 A/B 修复 + 修复落地与验证

背景

message-queue-enhance 是我们一个 Rust 组合服务（单端口 8080）：

  • /forward/ws —— 反向隧道控制面（Reverse Forwarder 协议：公网端口 → Nginx 客户端 → 内网服务）
  • /ws、/mq/ws —— 消息中继（WebSocket 发布/订阅）
  • /mq/status —— 组合仪表盘（SSR HTML，5 秒自动刷新）

部署后不久服务"异常"：/mq/status 无法访问，TCP 显示还在监听 8080 端口，但 curl 或 websocat 连接都没有任何反映。

这篇文章是"调试工具与方法论"视角的完整记录：没有一次定位，没有灵光一闪，只有一步步用 /proc、日志、core dump 把"还活着"证明成"其实死透了"。文章会随深度排查持续更新。

现象

$ curl http://<server>:8080/mq/status      # 超时，0 字节应答
$ curl http://<server>:10200/mq/status     # 超时（同服务经 caddy 代理）
$ curl -k https://<server>:9000/mq/status  # HTTP 200 但 body 空！

端口探针/ss 显示 8080 仍在 LISTEN，进程还存在（容器 docker ps Up 状态），但一切请求都像被黑洞吞掉。

第一课：TCP 能连通 ≠ 服务可用。 内核层监听（backlog 队列）和用户态 accept/处理是完全两回事——ss 显示 LISTEN 只证明了内核 socket 还在。

排查过程

第一步：确认"谁在听、谁在等"

先搞清楚 8080 上到底有什么 socket 坐着：

# 容器 netns 内查看（宿主侧 lsof）
sudo nsenter -t <host_pid> -n lsof -nP -iTCP:8080

结果（关键几行）：

caddy      <pid>  TCP 127.0.0.1:32768->127.0.0.1:8080 (ESTABLISHED)   # 反向代理一条连接挂死
message-q  <pid>  TCP *:8080 (LISTEN)                                 # 主服务在听
message-q  <pid>  TCP 127.0.0.1:8080->127.0.0.1:xxx (CLOSE_WAIT)      # 积压的半关闭连接（对端已 FIN，服务端从未 close）

要点：

  • CLOSE_WAIT：对端已 FIN，服务端应用从未 close 这个 socket —— 应用早就"不干活"了，只是进程没退出。
  • 真实客户端链路：agent 侧经 caddy 的 10200 端口反代（Caddyfile：handle /forward/ws、handle_path /mq* → reverse_proxy {$MQ_WS}，MQ_WS=http://127.0.0.1:8080）到达 message-queue-enhance 8080 —— caddy 到 8080 的那条 ESTABLISHED 挂死正是代理转发的请求等不到上游响应。

第二步：日志时间线——两轮运行完全同构的结尾

日志文件 message-queue-enhance.log 最后的写入时间是冻结时刻，之后 40 分钟没再增长（哪怕每 5s 自动刷新的 /mq/status 也没触发任何日志写入）。提取最后部分：

06:52:13.647  message-queue-enhance listening on 0.0.0.0:8080      # 服务启动
06:52:40.924  request method: GET, uri: /forward/ws?remote_port=9171...   # 客户端对 A
06:52:40.924  response status: 101 Switching Protocols                  # A 对成功注册
06:58:37.406  request method: GET, uri: /forward/ws?remote_port=8172...  # 客户端对 B 来
06:58:37.406  response status: 101 Switching Protocols                 # B 对第 1 条成功
06:58:37.406  request method: GET, uri: /forward/ws?remote_port=9172...  # B 对第 2 条：请求已记录
06:58:39.6    tunnel ...: listening on 0.0.0.0:8172 ...                # 但 9172 永无后续
06:58:48.409  request method: GET, uri: /forward/ws?remote_port=9172...  # 恰 11.003s 后客户端重试
06:58:48.409  <没有 response 行>                                       # 第二次也卡死
（之后 40 分钟无任何日志）

冻结模式（这是本次最重要的发现）：

  1. 旧隧道对（A）仍存活时，新客户端对 B 注册 /forward/ws
  2. B 对的其中一条升级"卡死"：TraceLayer 已打印 request method，但永远没有 response status: 101、没有 registered、没有 listening
  3. 恰好 11.003 s 后客户端重试同一端口——同样卡死
  4. 随后整个 runtime 冻结：无日志、无响应

再回看上一轮容器运行（前一天启动的那次），结尾完全同构：

03:42:26.515  request method /forward/ws?remote_port=8171   # 第 1 条卡死
03:42:26.515  request method /forward/ws?remote_port=9171   # 第 2 条成功 101
03:42:37.518  request method /forward/ws?remote_port=8171   # 11.003s 后重试也卡死
（之后 3+ 小时无日志，直到人工重启）

这不是偶发，是可复发的 bug 模式。 两轮运行、不同的挂起端口（这次 9172、上回 8171），模式一模一样的"11 秒重试→全灭"。

第三步：进程是否真的活着？——/proc 线程状态

ps 显示进程在、CPU 0、无 panic。到底每根线程在等什么？

for t in /proc/<pid>/task/*/; do
  echo "$(basename $t): $(cat $t/wchan)"
done

结果：

16 × tokio-rt-worker : futex_wait_queue      # 全部 worker 处于 idle park
1  × message-queue-e  : futex_wait_queue     # 主线程（block_on）

对照健康实例（起一个同类服务对比）：

1 × tokio-rt-worker : do_epoll_wait          # ← 健康实例有且只有一个"轮询者"
N × tokio-rt-worker : futex_wait_queue       # 其余 worker park

冻结态：0 个线程处于 do_epoll_wait。 也就是说——tokio 的 io driver 没有任何线程在轮询。所有 fd（含 8080 LISTEN）都在 epoll 里注册着，事件来就绪时却无人消费。

这里我用了一个对照实验：直接在本机跑一个同样骨架的 tokio 服务，看它空闲时 wchan 的"分布样貌"。单看 wchan 值没有意义，看分布才有意义：futex_wait_queue 既可能是健康空闲、也可能是死锁——区别就看有没有人 do_epoll_wait。

第四步：是不是"锁死锁"？——core dump 裁决

futex_wait_queue 也可能是两个任务互相等一把共享锁。必须区分"锁死锁"还是"调度睡死"。手段：gcore 固化解冻态，再读每个线程的 futex 参数。

生成 core

# 服务器宿主侧（先确认 TracerPid=0，见下文的"插曲"）
sudo gcore -o /tmp/mq-core 1552056
# Saved corefile /tmp/mq-core.1552056   (36MB)
  • core 是手动生成一次的取证产物（与后文的 watchdog 自动 gcore 不同，watchdog 至今未触发）
  • 本地副本（排查用）：scp smyl@192.168.7.165:/tmp/mq-core.1552056 与生产二进制副本存入 ~/.tmp/opencode/mq-core/
  • 注意：core 内文件映射路径是容器内 /message-queue-enhance——gdb 会报"路径映射"警告（warning only，可完全忽略：gdb 以命令行提供的 exec 文件为准，分析照常）。真正的前置只有 exec 文件的 .text 布局与 core 匹配（同源构建=同布局；这就是"带 DWARF 的 debug 版"章节的意义）。"建同名路径/在容器内分析"只是消除该警告的手段，非必需。

配套系统调用证据（strace 曾成功捕获一次，attach 后主线程进入等待的参数）：

futex(0x792cd09b81d8, FUTEX_WAIT_PRIVATE, 1, NULL)   # 无超时私有锁等待；该地址=主线程 park token

⚠️ 插曲：排查自己也被"卡住"——TracerPid 与残留 strace

排查途中想用 strace -p 观察，先 attach 成功（后台化时命令挂掉导致 strace 变孤儿进程还挂在目标上）；随后所有 gdb/strace 都报 ptrace 不允许，最后在 /proc/<pid>/status 发现：

State:  S (sleeping)
TracerPid: 208     # ← 进程已被别的 tracer 占用！

kill 掉残留 strace 后（内核自动 detach），TracerPid 回到 0，gcore 才可附加。教训：一个进程同时只能有一个 tracer；strace 不做后台化就死掉，会留下"附身"痕迹——排查工具本身也污染现场。

解栈：gdb 的 bt 为什么断掉？如何手工补？

对 core 用 gdb -batch -ex "thread apply all bt"，结果几乎全是问号，栈在一个方向就断了：

#0  0x0000792ccfd468ee in syscall ()       # 断在 libc 裸汇编 syscall()
#1  0x0000792c00000008 in ?? ()            # 之后全废
#2  0x0000792ccdba2240 in ?? ()
...

原因（这次学到的重要知识）：

  1. 生产二进制是 static-pie、not stripped（有 .symtab 符号表）但 没有 DWARF（无 .debug_* 节）→ 没有行号/内联信息。
  2. glibc 的 syscall() 是裸汇编函数（无 .eh_frame）——即使有 .eh_frame，unwinder 到 frame0 也找不到"返回地址在哪儿"，直接放弃展开。
  3. Rust release 默认无 frame pointer，camera 依赖 CFI；CFI 断了就没法自动跳。

手工解栈方案（绕开 unwinder，一层层"读栈"）：

# 方式 A（推荐，一条 batch 命令批量完成）：
# -ex 是顺序执行的子命令；thread apply all 对每条子命令都逐线程执行，
# 因此 $rsp 自然跟随当前线程，无需手动抄地址
gdb -batch \
  -ex "thread apply all p/x \$rsp" \
  -ex "thread apply all x/16gx \$rsp" \
  ./message-queue-enhance ./frozen-core.1552056

# 方式 B（真正"交互式"，gdb 交互 shell 内手动分步）：
#   gdb ./message-queue-enhance ./frozen-core.1552056
#   (gdb) thread apply all p/x $rsp        ← 看输出抄下想关注的线程 rsp
#   (gdb) thread 2
#   (gdb) x/8gx 0x<上面抄来的地址>
#   (gdb) quit

比如线程 2 的原始栈：

0x792ccf9ff1e0:  0x0000792ccf9ff1d0  0x0000792c00000008
0x792ccf9ff1f0:  0x0000792ccf9ff240  0x0000792ccf9ff200
0x792ccf9ff200:  0x0000792cd09876b0  0x0000792ccf9ffad0
0x792ccf9ff210:  0x0000000000000080  0x0000000000000001

其中 0x792cd09876b0 用 info symbol 解出是 tokio::runtime::task::waker::WAKER_VTABLE（tokio 内部静态全局对象，.data.rel.ro），而 0x792ccf9ffad0 是这个线程自己的 futex（park 令牌）。

WAKER_VTABLE 怎么用？ —— 确定二进制"基址"，从而把核心地址全部换算成偏移给 addr2line：

nm <binary> | grep waker_vtable            # 偏移 0x00f876b0
# 基址 = 0x792cd09876b0 - 0xf876b0 = 0x792cc0000000
addr2line -f -e <binary> <pc_hdr - 基址>

每一根线成什么样子？

  • 每个 worker 的 futex 地址都在它自己的栈区内（间距 2MB 规律）——tokio 每线程 CachedParkThread 的 park 令牌，不是共享锁。
  • 栈帧里能看到 WAKER_VTABLE 指针 —— 线程正处于 waker 回调/park 路径。
  • 最终判读：全部线程 = tokio 标准 idle park；共享锁死锁被排除。

结合 wchan + epoll 注册表，完整因果闭合：

fdinfo 显示 fd 仍在 epoll（结构完好）
   + wchan 统计显示 0 线程在 epoll_wait（无人驱动）
   = "事件就绪但无人消费"的调度级睡死

第五步：epoll 注册表——fd 都没丢

ls -l /proc/<pid>/fd | grep eventpoll       # fd 3、5 都是 anon_inode:[eventpoll]
cat /proc/<pid>/fdinfo/3                     # 内核 dump 的注册表

输出样例：

tfd:        9 events: 8000201d data: 792ccdda9a00   # 8080 LISTEN 仍在 epoll
tfd:        4 events: 80002019 data: 0              # eventfd
tfd:        8 events: 80002019 data: 1              # socketpair
...

events: 0x8000201d 逐位含义：0x80000000 EPOLLET（边缘触发）| 0x2000 EPOLLRDHUP | 0x10 EPOLLHUP | 0x8 EPOLLERR | 0x2 EPOLLPRI | 0x1 EPOLLIN。

结论：注册表完好——不是 io 注册丢了，是 io 驱动没人在跑。

排除项

  • ❌ OOM：VmRSS ≈ 5MB，不可能因内存问题
  • ❌ 崩溃/panic：日志无 panic 帧、线程数正常（17）
  • ❌ 进程退出/僵尸：容器 Up、LISTEN 在、TCP 可连
  • ❌ 端口冲突：ss 只有本进程监听 8080
  • ❌ 句柄耗尽：fd 只有 20 余个

结论（第一阶段：定性）

tokio multi-threaded runtime 的 liveness 丢失（调度级睡死）：

  • 进程"活着"但有 0 个线程在轮询 io driver（wchan 分布）
  • 所有任务/驱动都被丢进 idle park 且不再被唤醒（futex 在每线程 TLS park 槽、栈中有 waker 痕迹）
  • 内核侧 LISTEN/注册表完好、事件就绪无人消费（fdinfo 与 TCP 行为交叉验证）
  • 强相关的触发序列：旧隧道活着 → 新客户端对注册 → 其中一个 WebSocketUpgrade 请求"已读入、永不完成"（无 101、无 registered）→ 11s 后同一端口重试也"已读入、永不完成" → 全灭
  • 两轮运行完全同构（分别是 03:42 轮与 06:52 轮），可复发

⚠️ 尚未钉死的部分：挂起的 WebSocketUpgrade 与 runtime 睡死之间的精确因果链（是 hyper 连接任务持有某事导致驱动饿死？还是升级路径上某处丢唤醒？）。已知链路：真实 agent 客户端经 caddy 10200 反代到达 8080，但升级请求挂起点与代理层（buffering/协议/超时）是否相关仍待查——本地复现未包含 caddy 一层，是主要缺口。

复现成功（7.1 实验环境 + 重叠对模式）

环境搭建（终版拓扑：只要 mq:8080，无需 caddy）

在一台干净机器（Ubuntu/Debian 系、免密 sudo）上搭建：

# 2) 启动 mq（RUST_LOG=info！本二进制不设 RUST_LOG 完全静音）

先对齐：修复前的真实锁序（三个缺一不可的结构事实）

① 会话期永久持有 Ref            ws_handler::handle_new 的 let t = registry.get(&p)
                                （Ref=分片读锁）在 session::handle_session(&t, ...)
                                整个隧道会话存活期内被跨 await 持有 —— 直到会话结束，
                                不会像状态页读那样 100µs 就释放。
② 同分片双写者并发 insert       B 对（agent + vscode 两条隧道）同毫秒注册同一分片成对端口；
                                每个写者先 get(p)（读）再 insert(p)（写）。
③ 状态页 iter + get 锁序        collect_tunnel_rows 原样：registry.iter()（分片读锁遍历）
                                后逐个 *registry.get(&p).unwrap().state.read().await
                                —— 临时 Ref 跨 await 存活（原表达式如此）。

另一个事实修正（对前文"默认 4 分片"的补充）：DashMap::new() 默认分片数是 (可用核数×4).next_power_of_two()（dashmap 6.2.1 lib.rs::default_shard_amount）—— 本机 22 核 = 128 分片；只有 1 核环境才是 4。7.1 复现机实测命中≈1/4 与 4 分片吻合。 复现样本里显式 with_shard_amount(4) 把同分片概率顶到 100%。

server.rs — A 对会话（Ref 跨整个会话期持有）

/// A 对会话任务: handle_session(&t, ...) 原样锁序
///   registry.get(&port) (Ref = 分片读锁) 在整个会话期持有 (跨 await，永不释放)
///   期间偶发 state.write().await (teardown 路径: shard-读 跨 inner-写)
pub fn spawn_session(state: &AppState, port: u16, tunnel_id: &str) {
    let s = state.registry.clone();
    let stop = state.stop.clone();
    let ep = state.epoch_inner.clone();
    let tid = tunnel_id.to_string();
    tokio::spawn(async move {
        // 注册隧道
        s.insert(port, Arc::new(Tunnel {
            state: tokio::sync::RwLock::new(TunnelState::Active),
            tunnel_id: tid,
        }));
        // handle_new: let t = registry.get(&port)
        let Some(t) = s.get(&port) else { return };
        // handle_session(&t, ...): t (Ref) 持有至会话结束 — 永不 drop
        while !stop.load(Ordering::Relaxed) {
            // session.rs:87: *tunnel.state.write().await = Disconnected
            // (teardown 路径: shard-读锁仍持有，跨 inner-写锁 await)
            {
                let mut st = t.state.write().await;
                *st = if *st == TunnelState::Active {
                    TunnelState::Disconnected
                } else {
                    TunnelState::Active
                };
            }
            ep.fetch_add(1, Ordering::Relaxed);
            tokio::time::sleep(Duration::from_millis(2 + (port as u64) % 5)).await;
        }
    });
}

client.rs — B 对并发注册（Barrier 同时性）

/// B 对注册: 每轮两个并发任务 get → drop → insert (ws_handler 原样)
///   Barrier 保证两个写者同时开始 (模拟生产"两个 WS 连接同毫秒到达")
pub fn spawn_registration_burst(
    registry: Arc<DashMap<u16, Arc<Tunnel>>>,
    ports: Vec<u16>,
    rounds: u64,
    stop: Arc<AtomicBool>,
    epoch_writer: Arc<AtomicU64>,
) {
    tokio::spawn(async move {
        for round_n in 0..rounds {
            let p1 = ports[(round_n as usize + 2) % ports.len()];
            let p2 = ports[(round_n as usize + 3) % ports.len()];
            let barrier = Arc::new(tokio::sync::Barrier::new(2));

            // 两个写者任务同时开始 (模拟 agent + vscode 两条隧道同毫秒注册)
            let w1 = tokio::spawn({
                let (s, ep, b) = (registry.clone(), epoch_writer.clone(), barrier.clone());
                async move {
                    b.wait().await;
                    let _e = s.get(&p1);
                    drop(_e);
                    s.insert(p1, Arc::new(Tunnel { /* ... */ }));
                    ep.fetch_add(1, Ordering::Relaxed);
                }
            });
            let w2 = tokio::spawn({ /* 同上 */ });
            let _ = (w1.await, w2.await);
            tokio::time::sleep(Duration::from_millis(rand_ms())).await; // 7-12s
        }
    });
}

watchdog.rs — 冻结检测 + wchan/gdb 取证

/// 监控 3 路进度, 写者 5s 无进展 → HANG (insert 永久卡死)
pub async fn run(&self, max_secs: u64) {
    let mut last = (0, 0, 0);
    for i in 0..max_secs {
        tokio::time::sleep(Duration::from_secs(1)).await;
        let cur = (
            self.epoch_status.load(Ordering::Relaxed),
            self.epoch_writer.load(Ordering::Relaxed),
            self.epoch_inner.load(Ordering::Relaxed),
        );
        // 冻结判定: 全停 或 写者卡死 (writer=0 持续 5s)
        if (i >= 2 && cur == last) || (i >= 5 && cur.1 == 0 && last.1 == 0) {
            println!("HANG: insert() 永久卡死, writer=0 (status={} inner={} 仍活)", cur.0, cur.2);
            dump_threads();  // /proc/self/task/*/wchan 分布
            try_gdb();       // gdb -p <pid> -batch -ex 'thread apply all bt 10'
            std::process::exit(42);
        }
        last = cur;
    }
}

为什么先前"纯库压测"钓不出来（被饿死 vs 真的死锁）

第一版（std 线程、任意读写风暴、8 组 × 60-120s）未冻结，只复现"写者 1 op/120s 的饿死"。现在回看：那版缺的正是上面 ①②③：

  • ① 缺会话期永久 Ref：读者最长持锁 2-5ms（sleep 版）→ 锁总是快速在读者/写者间流转，坏状态 1ms 内被下一个读者修复；生产里 A 对会话的 Ref 跨整个会话持有（秒~分钟级），把"读写者同时 parked"中间态的寿命拉到 B 对 insert 必然撞上的尺度；
  • ② 缺同分片双写者突发：泛化压力里写者是"打地鼠"，读多写少，两个写者同毫秒对称对垒的形态不出现；
  • ③ 缺 tokio 任务调度：Barrier 同时性 + 16 worker 轮流被任务 park 阻塞的 runtime 语义（纯 std 线程是亲自动作，任务模型里插队/抢占全由 scheduler 决定）。

顺带收获：DashMap::new() 默认分片 (核数×4).next_power_of_two()（22 核=128），泛化压测用 with_capacity_and_shard_amount(4) 但读者 32-Ref 时分片内重入计数与 ONE_WRITER 同空间的风险也有别的坑——不多展开，直接以"固定 4 分片 + 生产锁序"为正确路径。

strace / gcore / gdb 的边界

  • 一个进程同时只能有一个 tracer：/proc/<pid>/status 的 TracerPid 非 0 时，任何新 attach 都会失败（ptrace 不允许）。排查中自己就跑出过孤儿 strace 卡住进程——工具也要清理现场。
  • 容器进程通常没有 CAP_SYS_PTRACE（docker 默认能力集），strace -p/gdb -p 直 attach 会 EPERM；sudo 在具备 CAP_SYS_PTRACE 的 ns 下可行。
  • core 的文件路径映射：core 记录的是生成时的绝对路径（容器内如 /message-queue-enhance）。在另一台机器分析时 gdb 会报路径警告——要么在相同路径环境分析，要么以命令行 exec 文件为准（警告可忽略）。
  • 没 DWARF + 裸汇编 syscall() 无 CFI → bt 断 frame0：改用 x/8gx $rsp 读栈、info symbol/nm 手动符号化；先找一个已知符号（如 WAKER_VTABLE）运行时地址反推 static-pie 基址，把一切地址转偏移。

  • 决定 .text 布局的是：源码 + Cargo.lock + rustc 版本 + profile（opt-level/codegen-units/lto/panic 等）

附录：QA 记录（排查中的高频疑问）

Q1：dashmap 为什么 insert 会死锁？是版本不对还是代码问题？

都不是"版本用错"，但两者都有贡献——双因叠加：

  1. dashmap 6.2.1 的锁本身有真实薄弱点：它的 RawRwLock（dashmap/src/lock.rs）不是 parking_lot 原生锁，而是用 parking_lot_core::park/unpark 手写的状态机锁（WRITERS_PARKED/READERS_PARKED/ONE_WRITER 位运算）。unlock_exclusive_slow() 在"读+写都有人 parked"时先把状态 store(WRITERS_PARKED)（此时 owner 位清零），再由两条路径分别 unpark——这个中间态 + 并发新读者（只查 ONE_WRITER、不查 WRITERS_PARKED）或新写者（CAS(0)）的窗口，可以造成写者唤醒丢失/饥饿（core 里"两个 writer 全部 park、无 owner"正是这个形态）。这是 dashmap 6.x 在重度读写并发下的已知类问题（后续版本/换实现多次修过）。
  2. 我们代码踩了 DashMap 文档红线：status.rs 的 let t = registry.get(&port) 返回的 Ref（分片读锁 guard）跨过了 .await 才 drop（t.state.read().await 期间 t 仍存活；dashmap 6 的 Ref 是 Send，所以编译能过）。读锁跨 await 与并发 insert 交织，会大幅放大 1 的死锁窗口。

结论：库的固有弱点 × 我们的跨 await 用法 = 平时不炸、只在"唤醒/状态页并发"场景炸。两个都要修（一个换锁、一个守纪律）。

Q2：park_condvar 不是带 timeout 的 condvar 等待吗？为什么 timeout 唤醒不救场？

要点：timeout 到点唤醒 ≠ 能干活的资格。tokio worker 空闲 park 的 timeout 只取自"是否存在待处理的 timer"（无 timer 时是无限等）；即使醒来的 worker：

醒来 → ① 本地/全局队列没任务
     → ② 尝试 poll driver（epoll/timer）
     → ③ 发现 driver owner 令牌被死锁线程持有 → 没有资格轮询 → 继续睡回去

tokio 的 io/timer driver 是单 owner 防惊群设计：只有一个 worker 真正在 epoll_wait。驱动令牌被卡在 dashmap 锁里的 worker 占死 → 其他 worker 每醒一次都在 ③ 被挡回——timers（livetick 5s）与 socket 事件永远没人轮询，这就是冻结期间 livetick 停打印、连接无人 accept 的机制。

Q3：只是两个 worker 死锁在锁上，为什么整个 runtime 都 hang？

不只看"锁住 2 个"——真正的扩散机制：

1 个 handler 卡死（dashmap 写锁，无人持有者却无人归还该锁）
└─ 该 worker 恰正持有 io/timer driver 令牌
   └─ epoll 无人轮询 → 新连接与 timer 永不就绪
      └─ 其余 worker 无限 idle-park 等唤醒，永远等不到（唤醒信号源断供）
         └─ 全 runtime 静默死透（不是全部锁死，是"唤醒源断供"）

核心结论：tokio 里"一个 task 长时间阻塞"与"全 runtime 挂"之间，隔着"driver 令牌"这一环——修复重点不是多留几个 worker，而是绝不让 worker 在持驱动令牌状态下长时间阻塞（handler 路径消除共享锁长阻塞、加超时兜底）。
