工具链迁移 Wayland：剪贴板踩坑与适配方案

八月 09, 2026 [linux, wayland] #wayland #clipboard #wl-clipboard #tmux #virtio-gpu #waypipe

背景

X11 时代复制粘贴很简单：xclip / xsel 全家桶，tmux、fzf、vim 里全是它们的影子。切到 Wayland 后，剪贴板不再由"全局 X server"统一管理，而是每个合成器（compositor）自己实现，工具链也得跟着换。

本文记录迁移到 Wayland 剪贴板工具链的完整踩坑过程与最终方案，包含一个容易误判的 waypipe 报错，以及虚拟机显卡升级（QXL → virtio-gpu 3D）的根治思路。

Wayland 的双剪贴板：clipboard 与 primary selection

X11 有三个 selection（primary / secondary / clipboard），Wayland 只有两个：clipboard 和 primary selection，它们不是同一个协议的两种用法，而是两套机制几乎一样、语义完全不同的协议。

协议层面

clipboardprimary selection
协议wl_data_device（Wayland 核心协议自带）wp_primary_selection（独立扩展协议，2024 年才进 stable）
触发方式显式复制：Ctrl+C / 右键复制 / 应用内"复制"按钮选中即复制：鼠标选中文本的瞬间，应用立刻设置 selection，没有"复制"这个动作
常用快捷键复制 Ctrl+C（终端 Ctrl+Shift+C）、剪切 Ctrl+X、粘贴 Ctrl+V（终端 Ctrl+Shift+V）；Ctrl+Insert / Shift+Insert 在多数场景也映射到 clipboard没有复制快捷键（选中即复制）；粘贴是鼠标中键单击；Shift+Insert 在部分终端（xterm 系、foot）粘贴 primary
粘贴方式Ctrl+V / 右键粘贴 / wl-paste中键单击（终端/编辑器里） / wl-paste --primary
生命周期持续到下一次复制或被显式清空下一次选中立刻被替换；多数合成器在焦点切换后清空
对应工具wl-copy / wl-pastewl-copy --primary / wl-paste --primary

易混点：Shift+Insert 的映射因终端而异——X11 传统（xterm）它粘贴 primary，GNOME Terminal 等则当作 clipboard 粘贴；Wayland 终端（如 foot）保留 X11 语义：Shift+Insert = primary，Ctrl+Shift+V = clipboard。

联系

两套协议的实现结构完全同构：data_source（数据提供方）+ data_offer（数据接受方）+ data_device（会话对象），走同一套 MIME 类型协商机制。wl-copy 加不加 --primary 只是往哪套协议上挂 source。

部分合成器提供"联动"选项（比如选中文本时同步写入 clipboard），但那是合成器的额外实现，不是协议保证的行为——迁移时不要假设 Ctrl+C 和选中是同一个剪贴板。

wl-copy 工作原理：为什么复制工具必须常驻

理解了这个机制，前面表格里"daemon 常驻"和"管道挂死"两个坑就都说得通了。

惰性传输（lazy transfer）

Wayland 剪贴板不是"复制时把数据交给合成器"，而是"注册一个数据源，谁要粘贴谁自己来取"：

复制方(wl-copy)                    合成器                      粘贴方(wl-paste)
     │ 创建 data_source               │                           │
     │ 声明 MIME(text/plain 等)        │                           │
     │ set_selection(source) ───────►│                           │
     │                                │── 收到 data_offer ───────►│
     │                                │◄───── receive(mime, fd) ──│
     │◄── send(mime, fd) 回调 ────────│                           │
     │ 把数据写进 fd ──────────────────────────────►               │
     │                                │                           │

关键点：数据在"复制"时刻并没有传输。合成器只记下"当前剪贴板内容是哪个进程提供的"。直到有人真的执行粘贴，合成器才会回调数据源进程的 send() 回调，把数据中转到粘贴方。

所以数据源进程（wl-copy 的守护进程）必须活着——它死了，合成器就只能给粘贴方一份空数据。xclip 常驻是同一个道理。

wl-copy 的执行流程

  1. 读入全部 stdin（或参数/文件内容），按内容推断 MIME：UTF-8 纯文本 → text/plain;charset=utf-8，含 NUL 字节/非 UTF-8 → application/octet-stream
  2. 内容先落到临时缓冲（/tmp/wl-copy-buffer-*/ 目录 + memfd），大剪贴板（截图、视频帧）不会撑爆内存——实测守护进程的 fd 列表里能看到这个文件
  3. 连接合成器，创建 wl_data_source，声明 MIME
  4. set_selection() 提交 → fork 守护进程：父进程退出，子进程保持 wayland 连接，等待 send() 回调
  5. 每次有人粘贴，把缓冲里的数据写进合成器给的 fd；被新复制替换或收到 release 后退出

这解释了两个坑

  • 管道挂死：printf x | wl-copy 卡住——守护进程 fork 时继承了管道读端 fd，shell 等管道 EOF 永远等不到
  • 异步报错：wl-copy/waypipe 的很多错误是"粘贴发生时"才触发的（比如前文的 dmabuf 报错延迟 15~60 秒才出现），不是复制那一刻

关键差异一：wl-copy 没有 -f 回显

X11 时代的经典管道：

xclip -i -f -selection primary | xclip -i -f -selection clipboard

xclip -f 会把 stdin 原样回显到 stdout，所以可以串联多个 selection。wl-copy 没有这个选项，wl-copy | wl-copy --primary 的第二段会读到空。

解法：先用临时文件接住数据，再分别喂给两个 wl-copy：

f=$(mktemp /tmp/wlyank.XXXXXX)
cat >"$f"          # 接住 stdin
wl-copy <"$f"      # clipboard
wl-copy --primary <"$f"   # primary

关键差异二：daemon 常驻 + 管道挂死

echo foo | wl-copy 在脚本里没问题，但放到管道链尾部会挂住：wl-copy fork 出的守护进程继承了管道读端 fd，shell 等管道关闭时永远等不到。

实测：printf x | wl-copy 在 bash 里能卡 120 秒以上。所以 tmux 绑定里不要写成管道，用文件重定向最稳。

关键差异三：没有全局剪贴板，只有 socket

Wayland 客户端通过 $XDG_RUNTIME_DIR/$WAYLAND_DISPLAY 这个 unix socket 连合成器。坑点：

  • tmux server 继承旧 socket：tmux server 是长驻进程，它启动时的 WAYLAND_DISPLAY 可能早已失效（会话退出、waypipe 重连后 socket 名都变了）。新 pane 继承 server 环境 → 复制直接报 Failed to connect to a Wayland server。
  • 多个 socket 并存：SSH 多会话 + waypipe 隧道时，/run/user/$UID/ 下可能同时躺着好几个 wayland-* socket，肉眼无法判断哪个有效。

解法（wlyank.sh 运行时自愈）：

# socket 失效时自动回退到最新可用 socket
if [ -n "${WAYLAND_DISPLAY:-}" ] && [ ! -S "/run/user/$(id -u)/$WAYLAND_DISPLAY" ]; then
  export WAYLAND_DISPLAY=$(ls -t /run/user/$(id -u)/wayland-* 2>/dev/null | head -1 | xargs -r basename)
fi

疑难报错一：dmabuf 错误其实是 waypipe 的

症状：tmux 消息行每隔一阵刷一条绿色报错：

$591700: 15.880863 [src/dmabuf.c:125] Failed to open drm fd for /dev/dri/renderD128: No such file or directory

第一反应是 wl-copy 的错——查了 wl-clipboard 2.2.1 源码，根本没有 dmabuf.c。报错格式 $pid: elapsed [src/xxx.c:line] 是 waypipe 的日志风格。

排查过程

  1. 看进程：机器上跑着 waypipe ... --display wayland-n49YaBhs server，wayland-n49YaBhs 正是 tmux 客户端在用的 socket——这个会话是经 waypipe 隧道转发的。
  2. 时间线吻合：waypipe 进程启动 60 秒后出现 60.485827 的报错，与每次复制/粘贴的传输时机对得上。
  3. 根因：waypipe 在隧道间传缓冲区时优先走 GPU dmabuf 直传，但这台虚拟机是 QXL 显卡，/dev/dri 下没有渲染节点 renderD128 → 每次传剪贴板都异步失败一次。
  4. 复制本身是成功的（waypipe/wl-copy 会回退到共享内存拷贝），纯粹是噪音——但天天刷也烦。

解决

waypipe 客户端加 --no-gpu：

waypipe --no-gpu ssh -t <server> 'env SUDO_ASKPASS=/usr/local/libexec/sudo-askpass sudo -A <command>'

--no-gpu 禁用 GPU 相关协议、改走共享内存拷贝。注意是客户端侧参数，而且当前已建立的隧道要重连才生效。

教训：报错文本里的源码路径 + pid 前缀是定位哪个程序在叫的关键证据，别被"看起来像剪贴板错误"带偏。先 grep 一下报错字符串属于哪个项目，再动手改。

tmux 剪贴板绑定最终形态

# copy-mode 按 y：复制到 wayland clipboard
bind -T copy-mode-vi y send-keys -X copy-pipe-and-cancel 'wl-copy'

# 鼠标拖拽：clipboard + primary + OSC52 兜底（ssh 远程无 wayland 时降级）
bind-key -T copy-mode-vi MouseDragEnd1Pane send-keys -X copy-pipe-and-cancel wlyank.sh

# prefix + M：切换成纯 OSC52 模式（copy-pipe-no-clear，适合连续选区）

wlyank.sh 完整逻辑：接 stdin → 校验/回退 WAYLAND_DISPLAY → wl-copy + wl-copy --primary（2>/dev/null 压掉连接噪音）→ myyank.sh 发 OSC52 兜底。

依赖关系也要理清：脚本放 ~/.my_local/bin（整目录软链，自动部署），绑定放 ~/.tmux.conf，apt 依赖 wl-clipboard 在根 run.sh 的 install_pre 里——新环境 bash run.sh default 一键落地。

根治方案：QXL → virtio-gpu 3D

以上都是"兼容性修补"。想让 dmabuf 真正可用，得让虚拟机有渲染节点。

原理

  • QXL：纯显示卡，没有 3D 加速，不提供 renderD128。
  • virtio-gpu + virgl：虚拟 GPU 支持 3D 加速，guest 里出现 /dev/dri/renderD128，dmabuf 直传可用（waypipe 也能开 GPU 传输了）。

操作（宿主机上）

# 停 VM，编辑配置
virsh shutdown <vm>
virsh edit <vm>

<video>
  <model type="virtio" heads="1" primary="yes">
    <acceleration accel3d="yes" rendernode="/dev/dri/renderD128"/>
  </model>
</video>

要点：

  • 图形输出走 SPICE（<graphics type='spice'>）才能用 virgl 3D；QXL 显示协议要改成 spice/virtio
  • 宿主必须本身有 render 节点（物理 GPU 或另一层 virtio-gpu），否则 rendernode 指向的节点不存在
  • guest 内核需要 virtio_gpu 模块（主线内核默认有），装好 mesa 的 virgl 驱动
  • 改完重启 VM，验证：ls /dev/dri/renderD128 存在即可

总结：Wayland 剪贴板适配检查清单

  1. 所有 xclip/xsel 换成 wl-copy/wl-paste，注意 --primary 与默认 clipboard 的区别
  2. 不要写 wl-copy | wl-copy 管道（无回显 + daemon 挂管道），用临时文件
  3. 长驻进程（tmux server）的 WAYLAND_DISPLAY 可能失效，脚本里做 socket 存在性检查 + 回退
  4. 遇到 [src/xxx.c] 格式的报错先确认属于哪个程序（本案例是 waypipe 不是 wl-copy）
  5. waypipe 隧道在无渲染节点机器上必加 --no-gpu
  6. 想根治 dmabuf：虚拟机升 virtio-gpu 3D（virgl），宿主需有 render 节点
  7. ssh 远程/无 wayland 场景，OSC52（myyank.sh）兜底不能丢
